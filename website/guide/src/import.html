Import

What happens between plugging in a card and seeing the new folder in your library: how sources are found, how the listing reads every file once, how duplicates are recognized, and how each copy is written and checked before the card is ever touched.

The two halves of an import

An import is two separate pieces of work that run on different threads and never block the window:

  1. The listing. As soon as a source is opened, a worker thread walks it, reads every picture from start to end, and hands out thumbnails, capture times and a digest for each one. While it runs, the import tab fills in, picture by picture. Nothing is written anywhere during this phase.
  2. The copy. When you press Import, a file job on one thread copies the pictures you kept, verifies each copy byte for byte, and enters each one into the library as it lands. Only after the job is finished, and only if you ask, are the originals removed from the card.

The split matters because a card is hostile input: it may hold a damaged file system, a picture that claims to be 4 GB, a folder loop, or a name with invisible characters in it. The listing reads it as an untrusted tree with fixed limits, and the copy trusts nothing the listing did not measure itself.

How cards, drives and cameras are found

The "Import from" list is built from three kinds of source, and asking for it never touches the disk. A background listing runs at most every 2 seconds; the list you see is the last result it cached, and a change in it (a card inserted or pulled) repaints the list. That is why a card you plug in while the import tab is open appears on its own within a couple of seconds.

Card
A mounted volume that holds a DCIM folder, the layout every camera writes. Dalíca imports from that folder, not from the volume's root, so the camera's own housekeeping files are never listed. The common spellings DCIM and dcim are checked directly; on Linux and macOS, where names are case sensitive, up to 4,096 entries of the root are also scanned for other spellings. A link named DCIM is not followed.
Drive
Any other removable volume. It imports from its root. The startup disk and network shares are never offered as drives.
Camera or phone
A device with a PTP or MTP interface, spoken to directly over USB by a reader written for Dalíca from the public PTP and MTP specifications. Each storage on the device (two card slots, say) can be opened on its own.

Where the volumes come from depends on the system: on Linux, the mount table in /proc/self/mounts (volumes under /media, /run/media and /mnt); on macOS, the entries of /Volumes; on Windows, the drive letters C to Z. A drive letter is shown as "Removable drive (E:)", any other volume by its own name ("EOS_DIGITAL").

Cameras over a cable

Reaching a camera directly over USB only works on Linux. Dalíca never takes a device away from the program or driver that already holds it, and on the other systems something always does:

SystemWhat Dalíca can reach
LinuxA camera or phone no other program has claimed, over USB. If the desktop's own MTP service already holds it (gvfs on GNOME, kio on KDE grab the device as soon as it is plugged in), the camera is listed as held, and that service's mount point is offered as a drive instead, read like any folder.
WindowsThe system's portable-device driver holds every camera and phone. They are listed with the system's reason and are not opened. A camera that also shows up as a card or a drive letter imports as that card or drive.
macOSNo USB path is built; the system's image-capture service claims cameras as they connect. A camera that mounts as a volume imports as a card or drive.

A camera takes one PTP session at a time. The listing, the copy and the removal share that one session, opened from a worker on first use and dropped when nothing needs it. Every transfer has a 5 second timeout and every transaction 60 seconds, so a camera that goes silent is noticed instead of hanging the import.

The listing

The listing walks the source through Dalíca's file-system layer with fixed bounds: at most 32 folder levels deep, links followed with loop detection, and at most 100,000 files. FIFOs, sockets and device nodes are never opened (opening one can block forever). Anything left out is reported as a warning in the status line rather than silently skipped.

Each regular file is then read once, from start to end, in 64 KiB chunks:

  1. The first bytes are sniffed: a file is recognized by its content, not its name, and skipped unless it is a picture (or video) type that Options → File Types has turned on.
  2. As the chunks go by, the MD5 digest of every byte is computed, and the size is counted from the bytes actually read. The size the card reports is never used, so a file system that lies cannot make Dalíca allocate gigabytes.
  3. The first 256 MiB are kept in memory for the header and the thumbnail; the digest keeps going past that. A file that runs past 16 GiB is reported and not listed.
  4. The capture time is read from the picture's metadata (see below), and a thumbnail of at most 256 pixels on its long side is made, from the embedded EXIF thumbnail when it decodes, otherwise from a scaled decode of the picture, turned upright by its orientation.

Pictures are handed to the window in batches of 16, or every 200 ms when a batch has not filled, so the tray fills steadily even on a slow card. The listing checks its cancel flag between files: picking another source drops the old listing after the file it is reading.

For a camera the order is reversed, because reading bytes over USB is slow. The listing first asks the camera for every object's description and its own thumbnail, so the tray fills before a single picture's bytes are read. Only objects that need it are then read in full (at most 64 MiB each): those the duplicate check must compare, and those the camera has no thumbnail for.

Where the capture time comes from

For JPEG, PNG, WebP and TIFF files the date comes from the metadata reader, which resolves EXIF, XMP and IPTC into one "date taken". For raw files it is the EXIF DateTimeOriginal of the header. When the file records no date at all, the file's modification time is used, read as UTC. Each candidate remembers which of the two it got (timeSource is metadata or file). For a camera, the date is the one the camera gives the object, else its modification date. A file whose time cannot make a date at all is left out with a warning.

Why the file time is read as UTC: it is the one choice that gives the same answer on every computer. A modification time is an instant, and turning it into a wall-clock date depends on the time zone of the machine doing the import; reading it as UTC means a card imported on a laptop set to another zone still gets the same folder names.

Groups: a new one after a two-hour gap

The tray groups pictures by capture time. The rule is simple and is applied once the listing ends: sort the pictures by time (ties keep their listing order), then walk through them and start a new group whenever a picture is more than 2 hours after the one before it. Exactly 2 hours stays in the same group.

The gap is always measured to the previous picture, never to the start of the group. A group can therefore span far more than two hours, as long as you never stop shooting for longer than that. A day of sightseeing with a photo every hour stays one group; a long lunch break splits it.

The sample card in this guide (12 pictures in DCIM/100DALIC, taken between 17:34 and 19:01) lists as a single group: its longest gap is 53 minutes.

Duplicate exclusion

With "Exclude duplicates" on (it starts from Options → General → "Detect duplicates while importing", on by default), a picture that is already in your library, or that appears twice on the same card, is shown dimmed and is not copied. A duplicate here means the same bytes, not a similar-looking picture, and it is decided in three steps, each cheaper than the next would be:

  1. Size. When the source is opened, the library's photos are grouped by their recorded size, from the index alone. A candidate whose size matches no library photo cannot be a duplicate of one.
  2. MD5. For library photos of the same size, the digest comes from the index when the index holds one that still fits the file (same size and modification time). A photo without one is read now (at most 1 GiB) and its digest is handed back to be kept in the index, the same way Find Duplicates keeps them, so the next import does not read it again.
  3. Bytes. When size and digest match, both files are opened and compared in full, 64 KiB at a time. Only an exact match is a duplicate.

The same three steps are then applied against the earlier pictures of the same listing, so two copies of one file on a card (a camera that wrote a picture to both slots, for example) import once. In the sample run for this guide, two of the card's 12 files had been copied into the library before; the listing marked exactly those two as duplicates of library photos, and the import copied the other 10.

The copy

Pressing Import plans the work on the window's thread from the listing alone, without touching the disk: which candidates to copy (the ones given, or all of them, minus excluded ones and, with Exclude duplicates on, the duplicates) and which folder each goes to. A destination inside the source being imported is refused, and so is an import while the source is still being listed. Then a single file job copies one file at a time.

Each file goes through the same steps, in this order:

  1. Check the source. The file must still exist and still have the size the listing read. A file that changed since it was listed is not copied and is reported.
  2. Write a temporary file in the destination folder, with a hidden name of the shape .<name>.dalica-tmp-<16 hex digits>, in 1 MiB chunks. Exactly as many bytes as the source's size must arrive; more or fewer mean the source changed while it was read.
  3. Make it durable: the source's modification time (and permissions on Linux and macOS) are put on the copy, then it is flushed to the disk with fsync.
  4. Verify: the copy is read back and compared with the source, byte for byte. A mismatch removes the temporary file and reports the picture as failed.
  5. Name it with a rename that never replaces an existing file. If the name is taken, the next candidate is tried: DSC_3003.JPG, then DSC_3003-001.JPG, DSC_3003-002.JPG, up to -99999. The folder itself is then synced, and the named file is checked once more to be the one that was verified.
  6. Enter it into the library on the window's thread: its folder, the photo with the facts read back from the copy, the star and rotation you chose in the import tab, and the digest from the listing.

Keeping the original modification time is what lets a later import of the same card recognize the files, and it is also the date a picture without metadata will sort by. The import also keeps the file's name exactly as the card spelled it.

A camera's copy works the same way with one difference: the bytes arrive over USB in chunks into a private staging folder inside the destination (.dalica-camera-…, which scans skip). After the file is committed there and given the camera's date as its time, it is read back and checked against the MD5 digest of what the camera sent, and only then moved to its name.

Folder naming

The destination is "Import to" (by default your Pictures folder) plus one folder chosen by "Folder name":

Text you type
Passed through the one name sanitizer Dalíca uses for every folder and file it names: path separators, the characters Windows forbids (\ / : * ? " < > |), control and bidirectional characters are removed; leading dots, dashes and spaces and trailing dots and spaces are stripped (no hidden folder, nothing that reads as a command option); the name is cut to the longest a file system allows; and a Windows device name such as CON gets a leading _. A name that is empty to begin with is refused.
Date taken (YYYY-MM-DD)
One folder per capture date, from each picture's own capture time (the file time, as UTC, when it has no date). A card spanning three days makes three folders.
Today's date
The session clock's date, in UTC like every date Dalíca derives from a clock.

A folder that does not exist is created exclusively (if another program creates it at the same moment, Dalíca imports into it rather than failing). A folder that already exists is simply imported into, with the -001 rule keeping both files when names collide. When the destination is not already inside a watched folder, it is added as a watched folder (Scan Always). The library holds every copy, with its size and time, before any rescan looks at the folder, and rescans wait while a file job runs, so the folder watcher never imports Dalíca's own copies a second time.

Undo Import

All the files one import copied form one library undo step, "Import". Undo sends each copy that is still unchanged to the trash and takes its photo out of the library; a copy you have since edited stays, with the reason. The folders an import made stay on disk, empty. Redo copies each file from the source again, under the name it got the first time, as long as the source is unchanged.

Removing the originals from the card

"Delete copied files from the card" is the one place in Dalíca that may delete a file permanently, so it is fenced in:

  • It only runs after the copy job has finished, and only after you answer "Remove the imported files from the card? This cannot be undone." The question has no default button: pressing Enter removes nothing. Automation (the control channel and MCP) can never run it.
  • It only touches files this import copied and verified. Duplicates and excluded files are never touched.
  • Each file is removed only while it still has the identity (file object, size, modification time) it had when it was copied, and its copy still has the identity the copy step verified. A file that changed on the card, or whose copy has since changed or gone, stays on the card.
  • Paths are checked against the folder that was listed: a path that leaves it, contains .., or goes through a link is refused.
  • The file goes to the volume's trash when it has one. Most cards have none; there it is deleted. A trash error is never turned into a delete; only the trash's own answer that the volume has no trash is.

For a camera, removal is a PTP DeleteObject for each object, sent only while the camera still reports the size and dates the object had when it was listed. Once any file has left the card, Undo Import is disabled with "The originals were removed from the card.", because redo would have nothing to copy from.

When a copy fails or the card is pulled out

A failure is always per file, and it never damages what was already copied:

  • One file fails (unreadable sector, changed since listing, verification mismatch, no free name): its temporary file is removed, the failure is recorded with its reason, and the job goes on to the next file.
  • Cancel stops after the file being copied. What was copied stays, is in the library, and forms the undo step.
  • The card is pulled out. The file being written fails before it gets a name, so no partial picture is left behind, and each remaining file fails with its reason (usually that it "is no longer on the source"). Everything copied before stays.
  • A camera is unplugged or goes silent past its timeout: the import stops after the file it failed on (there is no point trying the rest), and the status says so: "Import stopped: 11 of 40 pictures copied. The camera was disconnected."

An import that was cancelled or had failures does not close the import tab. It stays open on its result ("Import cancelled: 2 of 4 pictures copied"), listing each failed file with its reason (the first five, then "and n more"), and the question about removing files from the card is not asked at all.

Crash safety: if Dalíca or the computer stops in the middle of a copy, the only trace is a hidden temporary file in the destination folder. The card still holds every original, because nothing is removed from it until the whole import has finished and you have confirmed.
