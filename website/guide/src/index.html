How Dalíca works

This guide explains what happens inside Dalíca that you cannot see from the window: which files it reads and writes, how it keeps your photos safe, and why it was built the way it was. This first page lays out the principles and the overall machine; every later chapter zooms in on one part of it.

The principles, in technical terms

Dalíca is a folder-based photo organizer with simple editing. A handful of rules shape almost every decision in its code. Here is what each one means in practice.

Your folders are the library

There is no import step for photos that are already on your disk and no hidden copy of them. Dalíca shows the photos and videos in the folders you tell it to watch, and a move or rename inside Dalíca is a move or rename on disk. It never invents its own folder hierarchy and never moves a file on its own. The only time it copies photos is when you ask it to, from a memory card or another drive. On first run it offers your Pictures, Documents and Desktop folders; scanning the whole disk is not offered.

Originals are kept

An edit is a recipe: a short list of operations such as autofix() and rotate(90) stored as text. The thumbnails, the edit view and every export render that recipe on the fly. The photo's pixels change only when you explicitly Save, and Save first moves the untouched original into a hidden .dalica-originals/ folder beside it, so Undo Save and Revert can always bring it back. Captions, tags, places and date changes are also written into the file's own metadata (on by default, and you can turn it off), but that rewrites only the metadata blocks and never touches pixels.

Your work lives in small readable files

Everything you decide about a photo (star, caption, tags, hidden, recipe with its undo history, albums, faces, place) is written to a JSON file named .dalica.json in the photo's own folder. Here is the one Dalíca wrote after a star, a caption, two tags, an Auto Fix and a quarter turn in a test folder:

{
  "dalica": { "version": 1 },
  "photos": {
    "DSC_4402.jpg": {
      "caption": "Fushimi Inari, early morning",
      "changed": "2026-11-07T03:33:13.650Z",
      "star": true,
      "tags": ["kyoto", "temples"]
    },
    "DSC_4408.jpg": {
      "edits": ["autofix()", "rotate(90)"],
      "star": true,
      …
    }
  }
}

The file is printed the same way every time (two-space indentation, keys sorted, Unix line endings), so it diffs cleanly and survives sync tools. Keys that Dalíca does not know, written by a newer version or by another tool, are kept exactly as they were. Because the sidecar travels with the folder, a folder you move or copy outside Dalíca keeps its stars and edits.

The central library index is only a cache. It lets Dalíca open 100,000 photos without reading 100,000 files, but deleting it loses nothing except time: a rescan rebuilds it from the folders. The few files that are not rebuildable (the Folder Manager's list of folders and your preferences) are small JSON files in the library directory.

Pictures/Kyoto/
  DSC_4402.jpg               # caption and tags also in its XMP and IPTC
  .dalica.json               # everything you did, per photo
  .dalica-originals/         # appears on the first Save
~/.local/share/dalica/library/
  index.log  index.snap      # the index: a journal and a snapshot (rebuildable)
  folders.json settings.json # watched folders and preferences
  albums.json people.json    # album and people definitions (rebuildable from sidecars)
  lock                       # one Dalíca process per library
~/.cache/dalica/thumbs/      # thumbnail packs, one set per size

Those are the Linux locations; macOS uses ~/Library/Application Support/Dalica/Library and Windows %LOCALAPPDATA%\Dalica\Library. The full layout is in Your library on disk.

The UI never waits for the disk

The thread that draws the window never decodes an image, never touches the file system, never waits on a lock a worker holds and never blocks on a dialog. This is enforced, not hoped for: the fs crate marks that thread at startup, and in debug and test builds every file call made from it fails with OnUiThread, so a mistake breaks a test instead of causing a stutter for you. Answers the window needs while painting ("is this folder online?") come from caches that workers keep filled. Opening a library reads the index and shows it at once; scans, thumbnails and the verification pass all run in the background.

Private by default

Dalíca has no account and no telemetry. It makes no network request unless you ask for something that needs one: map tiles (off until you allow them) and face-model downloads. Face data (the numeric descriptors that let Dalíca group faces) stays in a cache file in the local library directory and is never written to sidecars, file metadata, logs or the network. Logs never contain captions, tags, people's names, face data or tokens.

Pure Rust, native on three systems

Dalíca is written entirely in Rust and draws its own interface with egui on wgpu (Metal on macOS, Vulkan on Linux, DirectX 12 on Windows). There are no C or C++ build dependencies in the product, no web view and no JavaScript; a build-time check (cargo xtask deps) audits the dependency list for native bindings. Every one of Dalíca's own crates starts with #![forbid(unsafe_code)] and denies unwrap, expect and panic! outside tests, so bad input becomes an error you can read instead of a crash. Some dependencies (the GPU stack, the trash, the image resampler, the video decoders) contain unsafe internally; Dalíca's code does not.

Why these rules: a photo collection outlives the program you organize it with. If your work lives in plain files next to the photos and the pixels stay untouched until you say so, you can switch tools, restore from a backup or open the folder on another computer and lose nothing.

The big picture

Dalíca is a Cargo workspace of 18 small library crates and two programs: the desktop app dalica and the headless dalica-cli. Three ideas hold it together: the crates are stacked in layers, every action goes through one command registry, and all slow work happens on background workers that feed caches.

Crates in layers

Each crate has one job and lives in exactly one layer. A crate may depend only on crates in lower layers (with two listed exceptions: edit and meta may use image), and a checker (cargo xtask layers) refuses a build that breaks the rule. Two more rules matter for you:

  • Only the top layer knows a window exists. Only ui, ui-kit, mcp and the two programs may use the GUI and GPU libraries. Everything below them runs the same in the window, in the command-line tool and in tests, which is why automation can do anything you can do.
  • Only fs writes to disk. The checker searches every other crate for the standard library's write, rename, remove, copy and create calls. So the atomic-write routine, the read-before-write check, the trash and the crash-test fault points live in one place, and every other crate goes through them. Never losing a photo describes that crate.

The library crate at the center is pure: no files, no threads. It holds the in-memory model (folders, photos, albums, people, tags, recipes, places), and the only way to change it is to apply an Op, which returns the inverse Op and bumps a revision number. Undo is simply applying the stored inverses. Everything the window derives from the library (tree rows, the light-table layout, counts, search results) is cached per revision, so drawing a frame costs the same at 100 photos and at 100,000.

The command registry: one seam

Every user action is a command with a stable id such as photo.star.toggle or folder.rename. Each command declares its label, its place in the menus, its default keys per context, a description of its parameters, its effect (a query, a library change, a write to photo folders, or something outside Dalíca) and its history (which undo stack it goes on). The menus, the keyboard, dalica-cli, the control channel and the MCP server all call the same Session::execute(id, params). That function checks that the command is enabled, runs it inside a panic guard, records exactly one undo step, and returns JSON.

The build this guide was written against lists 454 commands: 227 engine commands and 227 view-only commands (pane toggles, zoom, selection moves) that live in the UI crate. Because there is only one door, a test or a script that runs photo.star.toggle exercises exactly the code a click does. Automation shows the registry from the outside.

Background workers

The thread that owns the session (the UI thread in the app, the main thread in the CLI) hands every slow task to a worker and applies the result later, between frames:

  • The I/O worker does every write the session makes: index journal appends, sidecar writes (debounced to at most one per folder per second), snapshots, and the library's own JSON files.
  • Scan threads walk folders, follow file-system change events and run the periodic verification pass. Their results arrive as batches of Ops, applied a few hundred photos per frame so the light table fills in progressively.
  • The thumbnail pool has one worker per CPU core minus one, clamped to between 2 and 8, with priorities: the edit view's photo first, then the hovered photo, the visible thumbnails, the filmstrip, effect previews, prefetch, and background generation last. Requests for the same slot are merged.
  • File jobs are everything that writes photo files (Save, Save a Copy, Export) and every file operation (move, copy, rename, trash). They run through one runner with a cancel flag checked before each item, and a panic in one item fails only that item.

When work finishes, the owner applies it as one undo step. Session::flush() waits until every pending write has landed; the CLI calls it before it exits, which is why a dalica-cli run script never leaves a half-written sidecar behind.

Caches

Dalíca keeps three kinds of cache, and none of them holds anything you cannot get back:

The library index
index.log (a journal: one line per change, each with a CRC-32 in front) and index.snap (a snapshot the journal is compacted into). It records each photo's path, size, modification time, dimensions, dates, an EXIF summary and what you said about it. A torn last line is discarded; a bad checksum stops the replay at that record.
Thumbnails
A size ladder in device pixels: 128 and 256 for every photo at scan time, 512, 1024 and a screen-size preview on demand. They are stored as JPEG at quality 90 in a few large append-only pack files per size (never one file per thumbnail), 2 GiB by default. Thumbnails always show your edits.
Color sketches
A blurred preview of every photo in about 25 bytes, kept in the index and in memory, so any cell of the light table can be drawn on any frame without a disk read while the real thumbnail loads. Thumbnails explains the ladder and the sketches.
