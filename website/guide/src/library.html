Your library on disk

Dalíca keeps what you decide about your photos in small text files next to the photos themselves, and treats everything else it stores as a cache. This chapter shows those files byte by byte, explains how album order survives being spread over many folders, and lists what lives in the library directory and what you can safely delete.

Your folders are the library

Dalíca does not import photos into a database of its own. It shows the real files in the folders you told it to watch, and it never moves, copies or renames a file unless you ask for that (a move, a rename, an import from a card). A photo lives in exactly one folder; albums are lists of references to photos and never hold files.

Everything you type or decide about a photo is written to a sidecar file in the photo's own folder: stars, captions, tags, hidden flags, the edit recipe with its undo and redo lists, album membership and order, the folder's sort, face rectangles and who they are, places and date corrections. Captions, tags, places and date changes are also written into the photo's own metadata (XMP, IPTC and EXIF) so other programs see them, unless you turn that off. The library index in the library directory holds a copy of all of it, plus facts Dalíca can always work out again by reading the files.

That split decides what happens when something goes wrong. If the index is lost, a rescan reads the sidecars and the photos and rebuilds it. If a folder is moved to another disk, its sidecar travels with it. If you open the same folders in a second copy of Dalíca on another computer, the second copy sees the same stars and edits.

The index is a cache

The library index is what lets Dalíca open a library of 100,000 photos in a fraction of a second without reading 100,000 files. It is two files in the library directory:

index.log
A journal: one line per change, written and synced to disk as each change happens. Each line is an 8-digit hex CRC-32, a space and one JSON record. The first line is a header saying the format version and how many changes the snapshot already holds.
index.snap
A snapshot of the whole model in one checksummed record. Dalíca takes one in the background once the journal holds 10,000 changes or 64 MiB, writes it atomically and starts a fresh journal. Opening the library loads the snapshot and replays the journal after it.

Here are the first lines of a real journal, from a library made for this guide with four photos in a folder called Kyoto (paths shortened, long lines wrapped):

b5ee4f91 {"journal":1,"base":0}
3161de5e {"op":"addFolder","folder":{"id":1,"path":"…/Pictures/Kyoto"}}
5d9eb4dd {"op":"addPhotos","photos":[{"id":1,"folder":1,"name":"DSC_4402.jpg","size":1218094,
           "mtime":1794022317761,"width":1591,"height":2400,"date":null,"star":false}, …]}
8d4b931f {"op":"setFirstIndexed","indexed":[[1,1794022317767], …]}
1e05d4b9 {"op":"batch","ops":[{"op":"setSketches","sketches":[[3,"0V4qWoWqjAhn3fCGKpNMzc/m7PL8bK4A"], …]},
           {"op":"setColours","colours":[[3,9],[4,2],[2,2],[1,21]]}]}

Reading stops cleanly at the first line that is torn (no newline), fails its checksum or does not parse: everything before it is kept, nothing after it is trusted. A failed append (a full disk, say) is cut back to the last whole record before the error is reported, so one bad write never costs the changes after it. A damaged snapshot is set aside and the journal used when it still holds every change; if neither can be trusted, the index is kept aside as .corrupt-<time> and the library is rebuilt from the folders.

What only the index knows

A few things live only in the index, and every one of them can be worked out again from the files: each photo's file size, modification time and pixel size, its color sketch and color summary (the blurred preview and the colors color: searches use), its search facts (camera, video, geotagged), content digests, the time this library first indexed it, and the hashes of the metadata Dalíca last synced with the file. After a rebuild these are read again or start empty.

Deleting the index, tried

To check the claim that the index is disposable, the guide's test library was given stars, captions, tags, two edits and a three-photo album, and then index.log was deleted. Opening the library again showed an empty library (a missing index is a new one; only a damaged one triggers a rebuild on its own). Running library.rebuild (Help > Troubleshooting > Rebuild library in the app) walked the folder and brought back all four photos with their stars, captions, tags and recipes, the album with its members in their order, and the Recently Updated list.

What a lost index costs: time, and a little history. Recently Updated keeps the changes made in Dalíca, because their times are stored in the sidecar ("changed"), but a photo that only changed on disk counted as updated by comparing its file time with its first-indexed time, which is index-only. After a rebuild those photos drop out of the list. Face embeddings are cached by the index's photo ids, with each file's size and time, so a photo whose id changed in the rebuild is searched for faces again in the background; the face rectangles and names themselves are in the sidecars and do not change.

The folder sidecar .dalica.json

Each folder that holds something you decided gets one hidden file, .dalica.json. A folder you never touched has none: the file is created on the first change. This is the real sidecar Dalíca wrote for the test folder after these commands: stars on two photos, two captions, the tags kyoto, shrine and fox, Auto Fix on one photo, a crop and a quarter turn on another, an album of three photos, and one photo dragged to a new place in the album. Two keys were then added by hand to stand in for another program (x-colorLabel and otherTool), and one more change was made in Dalíca:

The file on disk has one value per line with two-space indentation; short objects are folded onto one line here to save room. Reading it from the top:

"albums" at the top
The name of every album with a member in this folder, keyed by album id (a followed by hex digits). It is there so an album can be recovered by name even if albums.json in the library directory is lost.
"dalica"
Dalíca's own bookkeeping: the format version, and "missing" when a photo's file disappeared while its entry still holds data (see the Scanning chapter).
"photos"
One entry per photo that has data, keyed by file name. Using the name as a JSON object key means JSON's own string escaping round-trips any name, including ones with quotes, brackets, semicolons or non-ASCII characters. A photo with nothing to say (no star, no caption, no edit) has no entry at all.
"star", "caption", "tags"
As you set them. An empty value (false, "", []) is written as no key at all.
"edits"
The recipe: the edit history in the order you applied it, one operation per string, in the same text the recipe API uses. DSC_4476.jpg was cropped and then turned a quarter; rotations are ordinary entries. A "redo" list appears when you undo an edit in the edit view, which is why that undo history survives a restart. Pixels never change until you Save.
"albums" inside a photo
Album id to position key: the photo's place in that album (next section).
"changed"
When Dalíca last changed what it says about this photo, in UTC with milliseconds. Recently Updated reads it. The second command batch (the album move and a new star) touched only the two photos it changed: their times moved on, the others kept theirs.
"otherTool", "x-colorLabel"
The keys added by hand. Dalíca does not know them, and the next write kept both, at their places in the sorted order.

Other keys appear when you use the features behind them: "hidden", "date" (a corrected date taken), "faces" with normalized rectangles and person ids, "geo" (a [latitude, longitude] pair with six decimals, or null when you removed a location so the file's GPS is ignored), "savedAs", a "folder" object for the folder's description, date, place, sort and custom order, and a top-level "people" object naming everyone with a face in the folder.

How it is written

  1. Debounced. A change marks the folder dirty. The writer writes each folder at most once per second, so a burst of stars becomes one write, and a crash loses at most the last second of changes in one folder, never the file.
  2. Merged. The writer reads the file on disk again, changes only the keys whose value differs from what the file says, and leaves every other key and value exactly as it found it. A file that already says what the model says keeps its bytes, even if it is spelled differently (a tag list in another order, an EXIF-style date).
  3. Printed deterministically. UTF-8, LF line endings, two-space indentation, and the keys of every object sorted by their UTF-8 bytes at every level, so photos sort by file name and two writes of the same content give the same bytes. Diffs stay minimal if you keep your photos under version control.
  4. Replaced atomically. The new content goes to a temporary file, is synced to disk, and is renamed over the old one, after checking that the file is still the one just read. A crash leaves either the old file or the new one, never a torn mix. Leftover temporaries (.dalica-tmp-*) are cleaned up by the next scan of that folder.

Other programs' data, and damaged files

Unknown objects and keys are preserved verbatim on every rewrite. A known key with a value of the wrong type (a caption that is a number) is not used, is reported once, and stays in the file until you set that field yourself. An edit operation Dalíca does not know is just another string: it keeps its place in the recipe and the operations after it still apply. Text past Dalíca's limits (16 KiB for a caption) is shown cut and kept whole in the file.

A sidecar that cannot be read at all is renamed to .dalica.json.corrupt-<timestamp> and kept. The folder shows a banner and nothing is written into it (no sidecar, no metadata write-back into its photos) until you choose Reset folder data or put a good file back. The list of such folders is kept in damaged-folders.json, so a restart or a rebuilt index does not quietly start writing there before you decide.

Why plain JSON

  • It travels with the folder. Copy a folder to a backup disk, a new computer or a shared drive, and its stars and edits go with it. No export step, no database to keep in sync.
  • Anyone can read it. A text editor, a script or another program can read and even edit it. Dalíca's job is to keep whatever it finds there.
  • It is small. Only photos with data get an entry, and empty values are never written.
  • It outlives the program. If Dalíca disappeared tomorrow, your captions and album orders would still be sitting in a format any language can parse.

The photo files themselves

With the default options, captions, tags, places and date changes are also written into each photo's XMP and IPTC. In the test folder, the three photos that got a caption or tags grew by 2.7 to 2.9 KB each, and kept their modification times (Dalíca leaves the time alone unless you turn on "Update file modification time on metadata changes"). The photo with only Auto Fix kept its exact size: edits never touch a file until you Save. Metadata writes rewrite only the metadata segments of a JPEG and keep every other byte, pixels included. When the sidecar and the file disagree, the sidecar wins and the file is rewritten at the next metadata write, except when another program changed the file's value since Dalíca last synced it, while Dalíca's stayed the same, in which case that change is imported.

Album order: position keys

An album's order spans many folders, and each member's place is stored in that member's own sidecar. If places were stored as numbers (1, 2, 3), dragging one photo to the front of a 300-photo album would renumber 299 others and rewrite the sidecar of every folder they live in. Dalíca stores a position key instead: a short string of digits and ASCII letters that sorts in album order by plain byte comparison, chosen so that a key always exists between any two different keys. Moving a photo gives it a new key between its new neighbors' keys, and only its own sidecar entry changes.

A key is a sequence of integers written in base 62 (0 to 9, A to Z, a to z, in byte order). Each integer starts with a head letter that says how many digits follow: a one digit, b two, and so on up to z; uppercase heads are for negative values. So a0 is zero, the first key of an empty album, and longer integers always sort after shorter ones of the same sign.

Simply halving the gap on every insert would add a digit every six inserts at the same spot. Instead, adding at the end or the start steps the first integer by a fixed 3,844, which leaves room for about twelve midpoint inserts on each side before a key needs another level. Measured on 10,000 inserts at one spot, the longest key was 6 bytes when appending, 6 when prepending, 8 when always inserting at the second place and 9 when always inserting right after the previous insert. Only repeated drops into the middle of the newest pair grow keys steadily, and even that took 2,379 inserts before a key passed the 512-byte limit. When a key would pass it, Dalíca rewrites the album's keys the way Sort Album By does.

Rebuilding an album means collecting every member from every folder sidecar and sorting by key; equal keys (possible after merging two libraries) sort by folder path, then file name. albums.json in the library directory keeps a copy of each album's order as [path, key] pairs, used only for the photos of a folder whose sidecar cannot be read.

The library directory

The library directory is, in this order: the folder named by $DALICA_HOME; in portable mode (a file named portable beside the program) data/library next to it; otherwise ~/.local/share/dalica/library on Linux ($XDG_DATA_HOME/dalica/library), ~/Library/Application Support/Dalica/Library on macOS and %LOCALAPPDATA%\Dalica\Library on Windows. --library DIR opens another one. After the rebuild above, the test library held only albums.json (514 bytes), folders.json (144), index.log (2,323), lock (empty) and settings.json (85); the other files appear when the features behind them are used.

Every one of these JSON files follows the sidecar's rules: unknown keys are kept, writes are atomic and happen only when the bytes change, and a damaged file is set aside as .corrupt-<time> rather than overwritten.

Thumbnails are not in the library directory at all. They live in Dalíca's cache folder (~/.cache/dalica/thumbs on Linux, ~/Library/Caches/Dalica/thumbs on macOS, %LOCALAPPDATA%\Dalica\cache\thumbs on Windows), which you can delete at any time; Help > Stats for Nerds shows its size and has a Clear Thumbnail Cache button. The Thumbnails chapter describes its format.

One Dalíca per library

Two processes writing the same index and the same sidecars would undo each other's changes, so a library is opened by one process at a time. Opening a library takes an exclusive operating-system lock on the file lock in its directory. The lock belongs to the process, so the system releases it however the process ends, a crash included; there is never a stale lock to clean up, and the file itself is never deleted (deleting it would race with the next launch). The library directory is meant to be on a local disk, because file locks on network shares are not reliable.

A second process that finds the lock taken gives up at once instead of waiting. Tried on the test library while a headless Dalíca held it, dalica-cli answered "the library at … is open in another Dalica process" and exited with code 3. The thumbnail cache has a lock of its own (thumbs/lock); a process that cannot take it uses a temporary cache for that session and says so.

A second launch hands its files over

Double-clicking a photo in your file manager while Dalíca is already running should show that photo, not fail on the lock. For your own library (the platform's default one: not --library, DALICA_HOME, a demo or a portable copy), the first Dalíca also takes a lock on instance.lock, listens on 127.0.0.1 only, and writes its port, process id and a fresh 256-bit random token to instance.json, readable only by you.

  1. A later launch finds instance.lock taken and sends its file paths with the token in one request: at most 64 absolute paths of at most 4 KiB each, on one line, within 5 seconds. Anything else is refused whole and nothing opens. At most 8 such launches are served at once.
  2. The running Dalíca brings its window forward and opens its photo viewer on the first file, then answers ok. It answers only once its window has taken the paths.
  3. The later launch exits when it hears ok. If it hears anything else (the first one is still opening, hung or quitting) it keeps trying, and after 10 seconds starts on its own. A file is never acknowledged and then dropped.

When the photo viewer opens on a library another Dalíca holds (another user's, say), it opens on an empty, read-only library of its own in a temporary folder: the photo is shown with its edits from its sidecar, and changes are disabled with "Dalica is already open".
