Automation

Everything you can do in Dalíca's window, a script or an AI agent can do too, through the same commands, with the same undo steps and the same safety rules. This chapter shows how that works, with real command lines and the replies they produced, and where automation is deliberately fenced in.

Everything is a command

Every action in Dalíca is a command registered with a stable id. A command module in the engine crate (one file per area, such as cmd/rotate.rs or cmd/delete.rs) describes each command with a CommandSpec:

id
the stable name, such as photo.star.toggle, folder.rename or export.run.
label, menu
the English label (also the key for translations) and its place in the menus, such as Picture/Star / Unstar. A menu item lights up when a command with its id is registered.
keys
default shortcuts, each with the context it works in (the library, the edit view and so on). Your own bindings are stored as overrides in settings.json.
params
a short description of the parameters, written for people and agents to read, such as {"ids":[PhotoId], "on":bool}. The real check is a typed structure per command: a wrong type, a missing field or an unknown photo id is an error, never a crash.
effect
query (reads only), library (changes the library and through it the sidecars), files (writes to photo folders beyond the sidecars: Save, Export, move, delete) or external (reaches outside Dalíca: opening another program, a download, changing system settings).
history
which undo stack the command's step goes on: library (Edit ▸ Undo in the library), photo (the open photo's own edit history, saved in its sidecar), or none (queries and view changes).
enabled, run
two functions: one says whether the command can run now and, if not, why (the reason shown on the status line); the other does the work and returns JSON.

The registry is easy to look at. dalica-cli commands prints it as JSON; here is the first entry:

    "effect": "library",
    "history": "library",
    "id": "photo.star.toggle",
    "keys": [
      { "context": "library", "key": "Ctrl+8" },
      { "context": "library", "key": "F4" },
      { "context": "editView", "key": "Ctrl+8" },
      { "context": "editView", "key": "Space" }
    ],
    "label": "Star / Unstar",
    "live": true,
    "menu": "Picture/Star / Unstar",
    "params": "{\"ids\":[PhotoId]}: stars them all, or unstars them if all are starred",

The build this chapter was written against lists 454 entries. 227 are engine commands: 83 queries, 111 library changes, 23 file writers and 10 with external effects; 69 of them go on the library undo stack and 10 on a photo's own history. The other 227 are view-only commands ("ui": true: pane toggles, zoom, selection moves, slideshow controls) that live in the UI crate but are listed in the same catalogue, so an agent sees one list.

One function behind every surface

The menus, the keyboard, dalica-cli, the control channel and the MCP server all end in Session::execute(id, params). That function:

  1. looks the id up (an unknown id is unknown_command);
  2. refuses a files command in a read-only session;
  3. asks the command's enabled function, and returns its reason if it says no ("Select some photos first.");
  4. runs the command inside catch_unwind, so a bug that panics becomes an internal error and the app keeps running;
  5. collects the inverse of every change the command made and records them as exactly one undo step on the history the spec names, labeled with the command's name ("Undo Set Caption");
  6. returns the result as JSON.

So a script that runs photo.rotate.cw goes through the same checks, makes the same sidecar write and leaves the same undo step as pressing Ctrl+R. This is also how Dalíca tests itself: one engine test runs every registered command with empty, out-of-range and wrong-type parameters and expects an error from each, and panic_hunt generates hostile parameters from each command's spec, so a new command is covered the day it is added.

dalica-cli

dalica-cli is the headless companion to the desktop app. It opens a library in its own process, with no window and no GPU:

$ dalica-cli
usage: dalica-cli <command>

commands:
  commands                                   the command registry as JSON
  run --library DIR [SCRIPT | -]             run a JSON-lines script ({"command": id, "params": {...}} per line;
                                             stdin when no SCRIPT or `-`); one JSON result per line
  run --library DIR --cmd ID [--params JSON] run one command
  inspect --library DIR                      the library as JSON: folders, photos, stars, repairs
  snapshot --library DIR -o OUT.png [--size 1400x900] [--scale 1] [--script STEPS.jsonl]
                                             a headless screenshot of the app; …
  mcp [--demo | --library DIR] [--compact] [FOLDERS…]
                                             the MCP server on standard input and output over a headless
                                             session (`mcp --help`); its --demo is deleted on exit
  --version                                  print the version, with its commit and build date
…
exit codes: 0 success, 1 a command failed, 2 a bad argument or script line, 3 the library could not be
opened (for example, another Dalica process has it open)

Every example below was run against a test library of its own, with HOME and the XDG_* folders pointed at a temporary directory, on copies of this guide's sample photos.

run: commands from a script

A script is one JSON object per line; blank lines and lines starting with # are skipped. Each line prints one result line. A command that starts background work (a scan, for example) finishes it before the next line runs, and every write is flushed before the program exits. First, a new library and a folder:

$ cat setup.jsonl
{"command": "folders.add", "params": {"path": "/…/photos"}}
{"command": "library.query", "params": {}}

$ dalica-cli run --library lib setup.jsonl
{"command":"folders.add","ok":true,"result":{"new":true,"path":"/…/photos","scanning":true}}
{"command":"library.query","ok":true,"result":{"offset":0,"photos":[{"date":null,"durationMs":null,"folder":1,
 "height":2079,"id":1,"kind":"still","name":"DSC_4141.jpg","star":false,"width":2400}, …],"total":5}}

Then some organizing and editing, with two deliberate mistakes at the end:

$ cat edit.jsonl
# star two photos, caption one, tag them, then Auto Fix and a quarter turn
{"command": "photo.star.toggle", "params": {"ids": [3, 4]}}
{"command": "photo.caption.set", "params": {"ids": [3], "caption": "Fushimi Inari, early morning"}}
{"command": "photo.tags.add", "params": {"ids": [3, 4, 5], "tags": "kyoto, temples"}}
{"command": "edit.apply", "params": {"ids": [4], "op": "autofix"}}
{"command": "photo.rotate.cw", "params": {"ids": [4]}}
{"command": "photo.star.toggle", "params": {"ids": [99]}}
{"command": "photo.caption.set", "params": {"ids": [3]}}

$ dalica-cli run --library lib edit.jsonl
{"command":"photo.star.toggle","ok":true,"result":{"ids":[3,4],"on":true}}
{"command":"photo.caption.set","ok":true,"result":{"caption":"Fushimi Inari, early morning","changed":1,"ids":[3]}}
{"command":"photo.tags.add","ok":true,"result":{"changed":3,"ids":[3,4,5],"tags":["kyoto","temples"]}}

A failed line does not stop the script; the exit status is 1 when any line failed. When it finished, the Kyoto folder's .dalica.json held the stars, caption, tags and the recipe ["autofix()", "rotate(90)"], and the caption and tags were also in the photo's XMP and IPTC, with its modification time untouched.

Undo is a command too. edit.undo without parameters walks the library stack; with {"id": …} it walks that photo's own edit history. A script can also be piped in on standard input with -:

$ printf '%s\n' \
  '{"command": "photo.caption.set", "params": {"ids": [6, 7], "caption": "Ring road, day 3"}}' \
  '{"command": "edit.undo"}' \
  '{"command": "photo.caption.set", "params": {"ids": [6], "caption": 42}}' \
  '{"command": "photo.rotate.cw", "params": {"ids": []}}' | dalica-cli run --library lib4 -
{"command":"photo.caption.set","ok":true,"result":{"caption":"Ring road, day 3","changed":2,"ids":[6,7]}}
{"command":"edit.undo","ok":true,"result":{"undone":"Set Caption"}}
{"code":"bad_params","command":"photo.caption.set","error":"bad parameters: invalid type: integer `42`, expected a string","ok":false}
{"code":"disabled","command":"photo.rotate.cw","error":"Select some photos first.","ok":false}

The undo stack lives in memory for the life of one process, so an undo has to be in the same script (or the same app session) as the step it takes back. A photo's edit history is different: it is stored in the sidecar ("edits" and "redo") and survives restarts.

Commands that ask a question in the window refuse until their parameters say "confirm": true, and the refusal carries the question's text:

$ dalica-cli run --library lib --cmd photo.save --params '{"ids":[4]}'
{"code":"disabled","command":"photo.save","error":"Saving writes your edits into the photo's file. Dalica first keeps the original, unchanged, in a hidden .dalica-originals folder beside it, so Undo Save and Revert can always bring it back. Send \"confirm\": true to save (and \"dontAsk\": true to stop asking).","ok":false}

Confirming never weakens the safety rules: a confirmed delete still goes to the trash, and a confirmed Save still keeps the original.

Throwaway libraries

--demo in place of --library DIR opens a persistent library of generated photos in the temporary folder; --demo-fresh makes a new one and deletes it, with everything in it, when the command exits. Neither reads or changes your own library or settings, which makes them the right place to try a script:

$ dalica-cli run --demo-fresh --cmd library.query --params '{"limit":3}'
{"command":"library.query","ok":true,"result":{"offset":0,"photos":[{"date":"2026-06-06T13:40:00",…,"id":1,
 "name":"IMG_0041.jpg",…},…],"total":60}}

In the demo libraries, ids are deterministic (folders numbered in tree order, photos in light-table order), so a script can name them and get the same photo every time.

run and snapshot act as you. Like any program you start in a shell, dalica-cli run and snapshot are not checked against the automation roots described below, and snapshot --library DIR is not read-only: its script's commands change the library. Point experiments at a copy or a demo library, never at the only copy of your photos.

Headless snapshots

dalica-cli snapshot opens a library, drives the real interface through the headless driver, waits for it to settle and writes one PNG. There is no window, no GPU and no network connection: egui's output is rasterized on the CPU by Dalíca's own renderer, with the same tessellation, blending and clipping as the GPU path, and because the Inter font is bundled and rasterized by Dalíca, a snapshot looks the same on Linux, Windows and macOS. A script line is one of {"click": widgetId}, {"key": "Ctrl+8"}, {"command": id, "params": {…}} or {"settle": true}:

$ cat tour.jsonl
# star two Iceland photos, Auto Fix a third, select two and look
{"command": "photo.star.set", "params": {"ids": [6, 8], "on": true}}
{"command": "edit.apply", "params": {"ids": [7], "op": "autofix"}}
{"click": "tree:folder:2"}
{"command": "select.set", "params": {"ids": [9, 10]}}
{"settle": true}

$ dalica-cli snapshot --library lib4 --script tour.jsonl -o tour.png --size 1400x900
{"frames":74,"height":900,"ms":201,"ok":true,"path":"/…/tour.png","scale":1.0,"width":1400}

The driver's frames advance a virtual clock (1/60 s per frame), so animations and settling do not depend on the speed of the machine. Each settle waits up to 18,000 frames for nothing visible to be pending. The first failing step (an unknown widget, a disabled command, a settle that times out) stops the script with its line number, writes no PNG and exits with status 1. --size is in pixels (each side 1 to 8,192) and --scale is pixels per point (0.5 to 4), so --size 2800x1800 --scale 2 lays out the same 1400 × 900 window at double resolution. Widget ids such as tree:folder:2, thumb:4 or button:tray.hold come from the widget registry, where every interactive widget registers its id and rectangle each frame.

The control channel

The control channel lets a script drive a running Dalíca: run any command, read the library and the view state, click widgets by id, press keys, open menus, and take screenshots. It is off unless the app is started with --control. With --headless the app opens no window at all and answers only the control channel, which is how the examples here were made:

$ dalica --headless --control 19147 --library lib --automation-write-root /…/out
dalica: headless, control on 127.0.0.1:19147, token file /…/run/dalica/control-19147.token

Loopback and a token

The server listens on 127.0.0.1 only. There is no option to bind another address, and if the port is taken the app exits with status 2 instead of choosing another port ("cannot listen on 127.0.0.1:19150: the port is in use (another Dalica, or another program)"), so a script can never end up driving a different instance. While it ran:

$ ss -ltn | grep 19147
LISTEN 0      128      127.0.0.1:19147      0.0.0.0:*

$ stat -c '%a %n' "$XDG_RUNTIME_DIR"/dalica "$XDG_RUNTIME_DIR"/dalica/control-19147.token
700 /…/run/dalica
600 /…/run/dalica/control-19147.token

The token is 256 bits from the operating system's random source, written as 64 hexadecimal characters into a file only you can read (mode 0600 in a 0700 folder on Unix; on Windows the file takes the permissions of its folder in your user profile). By default the file is $XDG_RUNTIME_DIR/dalica/control-<port>.token on Linux (or a run folder in Dalíca's cache), made fresh for each launch and deleted when the app exits; --control-token-file PATH names another. There is deliberately no way to pass the token on the command line, where other users could see it in the process list. It is never logged and never appears in a reply.

The protocol

The protocol is newline-delimited JSON: one request object per line, one reply per line, in order. The first line on every connection must be auth with the token; the token is compared in constant time. A short Python client shows what the server does with a connection that skips it, and with an HTTP request such as a web page might send:

(no auth) → {"id": 1, "method": "library.inspect"}
← {"code":"unauthorized","error":"the first request must be auth (control-protocol.md §2.2); closing the connection","id":1,"ok":false}

(http) → POST / HTTP/1.1
← {"code":"parse","error":"not a request: the line is not JSON; send one JSON object per line; closing the connection","id":null,"ok":false}

→ {"id": "auth", "method": "auth", "params": {"token": "<64 hex>"}}
← {"id":"auth","ok":true,"result":{"app":"dalica","pid":1214743,"protocol":1,"version":"1.1.0 (dev build)"}}

Any line that is not a JSON object with a string method, is longer than 1 MiB, or nests deeper than 64 levels gets one parse error and the connection is closed; nothing sent after it on that connection runs. That is what keeps a browser's cross-origin request to 127.0.0.1 from smuggling a command in its body: its first line is an HTTP request line, rejected before the body is read.

After auth, the main methods are engine.execute (run a command), engine.commands (the registry), batch (up to 256 steps), library.inspect, ui.state and ui.set, ui.inspect (the view state plus regions, dialogs and performance counters), ui.widgets, ui.clickWidget, ui.key, ui.type, ui.menu.invoke, ui.screenshot, ui.settle, the jobs.* methods and app.quit. A few exchanges from the session:

→ {"id": 1, "method": "engine.execute", "params": {"command": "photo.star.toggle", "params": {"ids": [5]}}}
← {"id":1,"ok":true,"result":{"ids":[5],"on":false}}

→ {"id": 4, "method": "ui.screenshot", "params": {"path": "/…/out/ctl.png"}}
← {"id":4,"ok":true,"result":{"headless":true,"height":900,"path":"/…/out/ctl.png","settled":true,"width":1400}}

→ {"id": 9, "method": "engine.execute", "params": {"command": "photo.rotate.cw", "params": {"ids": ["three"]}}}
← {"code":"bad_params","error":"bad parameters: invalid type: string \"three\", expected u64","id":9,"ok":false}

Requests run on the UI thread between frames, through the same code the mouse and keyboard drive, and obey the same rule: a handler never touches the disk or blocks; work goes to workers and the reply waits for it. Input methods (a click, a key) reply only after the input has been consumed by a frame and one more frame has been laid out, so the next request sees its effect. Long commands (scans, export, Save of many photos) run as jobs; by default the reply waits for the job, and a job still running 55 seconds into the 60-second reply deadline answers {job, pending: true} so it can be followed with jobs.wait. One engine.execute is exactly one undo step; a batch is not a transaction, each command step is its own step.

ui.inspect also reports the window's performance counters, read here after a few clicks (times rounded):

"perf": { "fps": 60.0, "frameMs": 0.77, "frameP95Ms": 1.76, "cellsVisited": 7, "sectionsVisited": 4,
          "treeRowsVisited": 6, "thumbTextures": 7, "placeholderCells": 0, "sketchCells": 2, … }

dalica-cli can also talk to a running app: run --connect 127.0.0.1:PORT reads the token from the default token file for that port and accepts script lines of either kind, {"command", "params"} or {"method", "params"}; --keep-going runs every line even after a failure:

{"command":"photo.star.toggle","ms":4,"ok":true,"result":{"ids":[11],"on":true}}
{"method":"ui.clickWidget","ms":12,"ok":true,"result":{"rect":[0.0,222.0,240.0,24.0]}}
{"method":"ui.screenshot","ms":138,"ok":true,"result":{"headless":true,"height":900,"path":"/…/out/connect.png","settled":true,"width":1400}}
{"code":"external_denied","command":"photo.openExternal","error":"`photo.openExternal` never runs over automation: it starts another program, which only the person at the computer may do","ms":0,"ok":false}

$ dalica-cli run --connect 127.0.0.1:19149 --cmd edit.undo
{"command":"edit.undo","ms":1,"ok":true,"result":{"undone":"Star / Unstar"}}

What automation may and may not do

A client that holds the token can do what you can do in the window, with one set of rules applied on top. They live in one module of the engine (automation.rs) that both the control channel and the MCP server call, and they apply to synthetic clicks and keys as much as to engine.execute, so a click on a button cannot reach what the command behind it may not.

Ids, not paths

Most commands address photos, folders, albums and people by library id. An id can only reach files already indexed under a watched folder, so those commands need no file-system permission at all. The commands that take a path (adding a folder, an export destination, Save As, an import destination, a screenshot or render file, a collage folder, a face model file) are checked against roots granted when the app or server was started:

Read roots
Folders automation may add to the library or read from: --automation-read-root DIR (repeatable), plus, for MCP, the folders named on its command line and the client's own roots. Watched folders can always be read again. With no read root, adding a folder over automation is refused (except in the demo).
Write roots
Where automation may create files: --automation-write-root DIR (repeatable). With none given, the system's temporary folder and <cache>/Dalica/automation/.

A path must be absolute and at most 4,096 bytes; a . or .. component is refused before anything is resolved, and on Windows so are device prefixes, streams and reserved names. Then the path is resolved through its links and compared with each resolved root component by component, so /photos-evil does not pass for /photos and a link cannot lead out of a root. Two more rules: nothing is ever written inside .dalica-originals/, and a screenshot or render is never written inside a watched folder, where it would turn into a library photo (an export or a Save As may be, since those join the library by design). New files never replace existing ones, except that a screenshot may replace a .png. From the session above:

→ {"id": 5, "method": "ui.screenshot", "params": {"path": "/…/photos/Kyoto/shot.png"}}
← {"code":"path_denied","error":"/…/photos/Kyoto/shot.png is inside a watched folder: it would become a library photo","id":5,"ok":false}

→ {"id": 7, "method": "engine.execute", "params": {"command": "folders.add", "params": {"path": "/etc"}}}
← {"code":"path_denied","error":"/etc cannot be read by automation: no read root was given (--automation-read-root, a folder on the command line, or an MCP client root)","id":7,"ok":false}

Destructive commands ask first

Every command that asks a question in the window refuses over automation until its parameters carry "confirm": true: deleting photos, folders and albums, Revert, removing all edits, the first Save, removing a folder from Dalíca, rebuilding the library. The refusal carries the dialog's text and buttons so an agent can show the question to its user:

→ {"id": 8, "method": "engine.execute", "params": {"command": "photo.delete", "params": {"ids": [1]}}}
← {"code":"needs_confirm","error":"`photo.delete` asks first in the app; send \"confirm\": true in its params to go ahead (prompt holds the question)",
   "id":8,"ok":false,"prompt":{"buttons":["Move to Trash","Cancel"],"dialog":"deletePhotos","text":"Move the selected pictures to the trash?","title":"Delete"}}

Automation has no way around the data rules either: delete goes to the trash, Save keeps the original, metadata writes merge. Native file pickers are never opened by automation: commands take their paths as parameters, and a picker requested by a synthetic click is replaced by an in-app stub answered with ui.filePicker.

Effects outside Dalíca

Ten engine commands have external effects. Without --automation-allow-external, automation is refused anything that uses the network (map tiles, place search, model downloads), changes your system settings (making Dalíca the default viewer) or chooses where the app may connect. Some effects are refused whatever was granted, because only the person at the computer should trigger them: Locate on Disk (for photos and folders), Open With, Open in External Editor, and deleting imported files from a card.

→ {"id": 6, "method": "engine.execute", "params": {"command": "photo.openWith", "params": {"ids": [3]}}}
← {"code":"external_denied","error":"`photo.openWith` never runs over automation: it starts another program, which only the person at the computer may do","id":6,"ok":false}

While a control request is playing input into the window, the app also refuses these commands if a synthetic key or click reaches them.

People's names

Without --automation-allow-people, people's names, nicknames and face rectangles never reach automation. The commands still run (naming a face works, and its reply carries ids only), but replies that would carry names give null instead, and searches run with names left out of the match, so a search for a guessed name finds nothing and no reply can tell a guessed name from an unknown one. Filtering by a person's id still works, since ids are not names. Face descriptors are never returned, whatever was granted. The one accepted gap: a folder's own name is data you chose, so a folder named after a person still shows inside photo paths.

Errors an agent can act on

Every failure has a stable code and an English sentence. The full set: parse, unauthorized, unknown_method, unknown_command, bad_params, disabled, needs_confirm, not_found, busy, path_denied, external_denied, unsupported, limit, timeout, unsaved, read_only and internal. Two deserve a word. unsaved means the change was applied and is undoable but could not be written to disk yet (a full disk, a missing drive); the writer retries every few seconds, and nothing is lost unless the app quits first. timeout means the reply did not arrive in time but the work may still have happened, so a client should inspect before retrying.

MCP for AI agents

dalica-cli mcp exposes Dalíca to AI agents through the Model Context Protocol: JSON-RPC 2.0, one message per line on standard input and output. The server is a thin layer over the same command registry, hand-written with no async runtime and no C dependencies. It runs in two modes:

Headless (the default)
dalica-cli mcp [--demo | --library DIR] [FOLDERS…] opens its own engine session with no window. Folders named on the command line are added as Scan Once and become read roots. Without a library, it works in a temporary one that is deleted on exit.
Connect
dalica-cli mcp --connect 127.0.0.1:PORT drives a running dalica --control PORT through the control channel, reading its token file, and adds UI tools (screenshot, click, key, menu, settle). The app's own roots and permissions apply; the bridge cannot widen them.

Wiring it into a client is the usual stdio shape, a command and its arguments:

{
  "mcpServers": {
    "dalica": {
      "command": "/path/to/dalica-cli",
      "args": ["mcp", "--demo"]
    }
  }
}

Tools

In headless mode against a library, tools/list answered 246 tools: 19 helpers and one tool per engine command (cmd_ plus the id with dots turned into underscores, so photo.star.toggle is cmd_photo_star_toggle). --compact lists only the helpers, for clients that struggle with long tool lists; command_run still reaches every command.

HelpersWhat they do
command_list, command_run, command_batchthe registry, one command, up to 256 commands (one undo step each)
doc_inspect, query_photos, photo_infothe library, a search with filters, everything about one photo
scan_folder, select_photos, set_metadata, create_albumorganizing; set_metadata changes star, caption, tags, hidden, place and date in one undo step
list_edit_ops, get_recipe, set_recipe, apply_editthe recipe; set_recipe refuses to drop operations it cannot interpret unless told to
render_preview, render_photoan image of the photo with its edits, through the same renderer as thumbnails, Save and Export; changes nothing
export, jobs_list, jobs_cancelexport as the Export dialog does; background jobs

The tool annotations that tell a client whether to ask its user first are derived from the registry, not written by hand: a query command is read-only and idempotent; a command that asks first (its parameters name confirm) or has an external effect is destructive; openWorldHint is false everywhere, because no Dalíca tool reaches the network. A test runs every command without confirm and fails if one answering needs_confirm is not marked destructive. From the session:

query_photos          {"destructiveHint": false, "idempotentHint": true,  "openWorldHint": false, "readOnlyHint": true,  "title": "Query photos"}
cmd_photo_star_toggle {"destructiveHint": false, "idempotentHint": false, "openWorldHint": false, "readOnlyHint": false, "title": "Star / Unstar"}
cmd_photo_delete      {"destructiveHint": true,  "idempotentHint": false, "openWorldHint": false, "readOnlyHint": false, "title": "Delete from Disk…"}

Failures of the operation come back as tool results with isError: true and the same codes as the control channel, so the model can read them and correct itself; protocol errors use JSON-RPC's standard codes. An escaped panic in a tool becomes an internal error and the server keeps serving. Long tools report progress when the request carries a progress token, and cancelling the request stops the job before its next photo; photos already done stay done, each written atomically. The server also offers live resources: dalica://library, dalica://commands, dalica://selection, dalica://edit-ops and dalica://photo/{id}.

Read-only sessions

dalica-cli mcp --read-only opens the session so that nothing is written to your library: commands that write files answer read_only, and every other change (sidecars, the index, metadata, settings) stays in memory and is gone when the session closes. The refusal lives in the engine's session itself, so no tool can step around it:

→ tools/call cmd_photo_star_toggle {"ids": [1]}
← {"ids": [1], "on": true}
→ tools/call cmd_photo_save {"ids": [5], "confirm": true}
← isError: true {"code": "read_only", "error": "Save writes files, and this session is read-only (--read-only)"}

Afterwards, the photo starred in that session was still unstarred in the library, and its folder had no sidecar. What a read-only session still touches: the library's lock file, the thumbnail cache, a damaged index set aside at open, and Dalíca's own stale temporary files.

Before you connect an agent: prefer stdio over the TCP channel, grant the narrowest roots, and use --demo, --demo-fresh or --read-only for an agent you do not fully trust. An MCP client may send what tools return (rendered photos, captions, paths) to a remote model; that is your choice when you connect it. Dalíca itself never makes a network request on behalf of a tool.
