Places

Where a photo's coordinates come from, where Dalíca keeps them, how they reach your files, and what the map does with the network. The short version: your places live on your disk, the map works offline, and the network is used only when you allow map tiles and the Places pane is open.

One place, three records

A photo's location (its geotag) can be recorded in three places at once, and Dalíca has to decide which one to believe:

The file
The camera or phone wrote GPS coordinates into the photo's EXIF block, and other applications may have mirrored them into XMP. For RAW files, an .xmp sidecar next to the RAW can hold them too.
The folder sidecar
Dalíca's own record in the folder, .dalica.json, has a "geo" key per photo when you have said something about its place.
The library model
What Dalíca holds in memory and in its index (index.log and index.snap in the library folder), rebuilt from the sidecars and the files whenever needed.

The model's word on a photo's place has exactly three states, and the difference between the last two matters:

StateIn .dalica.jsonMeaning
A point"geo": [64.803, -23.081]The photo is here. Latitude first, in degrees, stored with six decimals.
Removed"geo": nullYou removed the location. The photo is not geotagged, whatever its file's GPS says.
No wordno geo key at allDalíca has never been told anything, so the file's GPS (if any) is the photo's place.

Six decimals of a degree is about 11 cm of latitude, far finer than any camera's GPS, so rounding never moves a photo in a way you could see. It also makes "the same place" exact: photos whose stored points agree to six decimals are one place on the map, drawn as one marker with their count.

Why a separate "removed" state: if removing a location simply deleted the geo key, the next scan would find the GPS still in the file (for example when writing to files is off, or the file is read-only) and quietly bring the location back. null is a decision you made, and nothing read from a file overrides it.

Where coordinates come from

The file's GPS

When a scan reads a photo, the metadata reader looks for a place in this order and takes the first one that is complete:

  1. EXIF GPS IFD: GPSLatitude and GPSLongitude, each one to three rationals (degrees, minutes, seconds), signed by GPSLatitudeRef (S makes it negative) and GPSLongitudeRef (W). A missing reference is taken as north or east. A rational with a zero denominator makes that coordinate unreadable, and a point needs both coordinates.
  2. XMP: exif:GPSLatitude and exif:GPSLongitude, the XMP copies of the same values.

EXIF wins over XMP for the place (and for the date) because XMP copies of EXIF fields are often stale: an application changes the EXIF value and forgets the mirror. For captions, tags and ratings the order is the other way round.

For a RAW file, an .xmp sidecar is read on every scan whether or not Dalíca is set to write such sidecars. Dalíca looks for <stem>.xmp first (IMG_0001.CR3 gives IMG_0001.xmp), then <file>.xmp and the .XMP spellings. The sidecar replaces the XMP embedded in the RAW as a whole, but the RAW's own EXIF still comes first for the place.

How the file's GPS enters the library

The model, not the file, is the truth for what Dalíca shows. A file's GPS becomes the photo's point under these rules, always without an undo step (the place was already the photo's, so nothing you see changes):

  • No word yet: the photo takes its file's GPS as its point. For a new photo this happens in the same operation that adds it, after its .dalica.json entry was read, so a sidecar's word (including null) always comes first. A library indexed before geotags were read has those photos' files read again on the next scan.
  • Changed elsewhere: the index keeps a hash of the place as last read from or written to the file. If a rescan finds the file's place different from that hash while Dalíca's own point has not changed, another application moved it, and Dalíca follows the file. If the file lost its GPS, the point goes too.
  • Changed on both sides: Dalíca's point stays, and the Properties pane notes that the value was changed in another application.
  • Removed: a location you removed is never brought back, whatever the file says.

The Geotagged filter and the pin badge on thumbnails follow the same rule: the model's word, else the file's GPS.

The library's own geotags

Every place you set in Dalíca goes into the model first, as one library operation with one undo step, and from there into the folder's .dalica.json. That sidecar is what makes a geotag survive an index rebuild, a move to another computer, or a file that cannot be written: on a rebuild, the scan reads the sidecar's geo keys (null included) in the same operation that adds the photos, before any file's GPS is considered.

Everything that changes a geotag goes through the same command, photo.geo.set, whether it came from dropping photos on the map, the pin, Paste Location, an agent over MCP, or the CLI. Clear Location is the same command with null. Copy Location writes nothing at all: it keeps one point in memory for the session.

Folders left by the classic folder-based organizer

The per-folder INI file the classic folder-based organizer left behind can hold a geotag entry per photo, as decimal degrees lat,lon. While "Read photo data left by the previous organizer" is on (the default), a scan of a folder that has only that file reads the geotags into the model as points (rounded to six decimals), with everything else it holds. That file is never written. The first change you make in such a folder creates its .dalica.json, holding the full converted data; from then on the INI file is ignored.

Where coordinates are written

A geotag you set, change, paste, clear, undo or redo is written into the photo file while Options ▸ General ▸ Files ▸ Write captions, tags and places into photo files is on (the default). The metadata write queue runs on its own thread, batches a photo's changes, and writes once the photo has been left alone for a second. Every write merges into the file's existing metadata, is written atomically and is verified by reading it back. Pixels are never touched.

FormatWhere the place goes
JPEGEXIF GPS IFD, plus the XMP mirror when the file already has an XMP packet
PNGEXIF in the eXIf chunk (or the raw-profile text that held it), plus the XMP mirror
WebPthe EXIF chunk, plus the XMP mirror (a simple-format file is promoted to VP8X, the image data unchanged)
TIFFthe XMP mirror only; refused when no packet exists and the write starts none, or when EXIF already holds the place (it would win on reading)
RAWnever into the RAW; an .xmp sidecar when "Write XMP sidecars for RAW files" is on (off by default)
HEIC, AVIF, JPEG XL, PSD, GIF, BMP, videonever; .dalica.json keeps the place

How the EXIF part is written:

  • Latitude and longitude become three rationals each: whole degrees, whole minutes, and seconds in millionths of a second. The rounding is about 3·10-10 of a degree. The references are N/S and E/W.
  • A GPS IFD that has no GPSVersionID gets 2.3.0.0; an existing version is kept.
  • EXIF is edited in place or appended, never repacked, because maker notes often hold offsets counted from the start of the block. A value that fits where the old one was is written there; a larger or new one is appended and only its pointer changes.
  • Removing a place deletes the four latitude and longitude tags and their XMP mirrors, nothing else: altitude, GPS time and direction stay as the camera wrote them. The old bytes are zeroed when nothing else points into them, so a removed location does not linger in the file for a forensic tool to find.
  • A place alone never starts a new XMP packet. A packet that Dalíca starts for a caption, tags or a rating gets the place in the same write.

With the option off, nothing is written to files and .dalica.json keeps the place. A file Dalíca cannot write (read-only, on an offline volume, a format it does not write) keeps its old GPS while the model and the sidecar hold your point. When the two disagree, the sidecar wins for display, and the file is rewritten at the next write of that field.

Exporting without a location: Export's "Remove location from exported photos" is stronger than Clear Location. It removes the whole GPS IFD from the exported copy (altitude and time included) and never touches the original.

The offline base map

The Places pane always has a map, even on a computer that has never been online. Its bottom layer is compiled into the program: the world's land from Natural Earth at 1:110 million (public domain), converted into a compact file, land-110m.bin. It holds 128 rings (land outlines, and lakes as holes in the land before them) with 5,001 points stored as 16-bit hundredths of a degree, 20,398 bytes in all. The file is read as hostile input like any other (bounded counts, every point checked to be on the globe), each ring is projected once to Web Mercator and cut into triangles by ear clipping, so a frame only scales, offsets and culls them.

The map is Web Mercator with zoom levels 0 to 19 and 256-pixel tiles: at zoom z the world is 256 × 2z pixels square, latitudes beyond ±85.0511° are clamped to the projection's edge, and longitudes wrap so the map pans round the globe. From the bottom up, the layers are the sea and a graticule, the offline land, any downloaded tiles, the markers, the pin, the controls and the attribution line.

Markers closer than 32 points on screen are drawn as one with the sum of their counts, and split again as you zoom in. Typed coordinates in "Search for a place:" never need the network: decimal degrees (38.7116, -9.1389) or degrees, minutes and seconds (38°42'41.8"N 9°8'20"W), at most 256 bytes. Without hemisphere letters, latitude comes first; with them, either order works. Anything that is not exactly two coordinates is refused, never guessed at.

Downloaded map tiles

Detailed maps (roads, towns, terrain) come from a tile server: by default OpenStreetMap's standard tiles at https://tile.openstreetmap.org/{z}/{x}/{y}.png. Options ▸ Network ▸ Allow map tiles is off in a new installation. The first time the Places pane opens, a card asks whether to show map tiles from the provider. Either answer is remembered in settings.json (network.tilesAsked), so you are asked once; afterwards the switch lives in Options ▸ Network.

When tiles are fetched

Two conditions must both hold: Allow map tiles is on, and the Places pane is open right now. Every frame that draws the pane tells the session it is open; a frame that does not draw it (the pane closed, another pane chosen, a room in front of it) tells it the pane closed, which cancels the tiles on their way. Nothing is fetched at start-up, during scans, or with the pane closed. Turning the option off cancels whatever is in flight at once.

While the pane is open, the request for one view goes like this:

  1. The pane works out the tiles covering its visible box at its current whole zoom level (crossing the antimeridian if needed) and asks for them only when that set changes, never on every frame. One request covers at most 256 tiles.
  2. Tiles of the previous view that are not in the new one, and have not started, are cancelled. A tile already on its way is not asked twice. A tile that failed since the pane opened is handed back as a placeholder without a new request (up to 4,096 are remembered; reopening the pane tries them again).
  3. Each tile goes to one of two worker threads, so at most two tiles are downloaded at the same time. That is the tile usage policy of the default server: only the tiles on screen, no prefetching, no bulk download.
  4. The worker looks in the cache. A tile younger than 30 days is used without any request. An older one is deleted and fetched again (up to two attempts).
  5. The bytes are checked before they are trusted: at most 1 MiB (a longer reply is cut off as it arrives, whatever size it announced), at most 1,024 pixels a side (read from the image header before a single pixel is decoded), then decoded under the normal raster limits. A tile that fails any check becomes a placeholder and is deleted from the cache, so it is asked for again next time instead of being kept broken.
  6. The pane takes finished tiles each frame and keeps them as textures (at most 384, the least recently drawn dropped first). While finer tiles arrive, coarser tiles already held fill in; a placeholder draws nothing, so the offline land shows through.

The tile cache

Tiles are kept in a folder named tiles beside the thumbnail cache, so on Linux usually ~/.cache/dalica/tiles/. When there is no thumbnail cache, a temporary folder is used and removed with the session.

~/.cache/dalica/
  thumbs/                       the thumbnail cache
  tiles/
    <16 hex digits>/            one folder per server address
      6-28-16.tile              a tile: <zoom>-<x>-<y>.tile
      6-29-16.tile.part         a download in progress
    <16 hex digits>/            the geocoding service
      q-<16 hex digits>.json    one place-search reply
  • Folder names are the 64-bit FNV-1a hash of the server's address template, written as 16 lower-case hex digits. Changing the tile server therefore never mixes two servers' tiles, and switching back finds the old tiles still there.
  • Size: the cache is kept under 200 MB. When its own files add up to more, the oldest (by modification time) are deleted until it is at 160 MB, four fifths of the budget. It is checked by the first job of a session and again after every 16 MiB added.
  • Age: a tile or search reply older than 30 days is asked for again the next time it is needed.
  • Safety: pruning lists and deletes only files of the cache's own name shapes (<zoom>-<x>-<y>.tile, q-<hex>.json and their .part files) inside folders of the 16-hex-digit shape, never follows links, and looks at no more than 200,000 entries. A file you put in that folder yourself is left alone.

The cache is the reason a familiar area appears instantly and offline: once a tile is on disk, nothing goes out for it for a month. Deleting the tiles folder is always safe; it holds nothing but copies of public map pictures and search replies.

What goes over the network

A tile request, byte for byte

Requests are built by one function in dalica-fetch, whatever carries them, so the list below is complete. For the tile 6/28/16 on the default server, Dalíca sends:

GET /6/28/16.png HTTP/1.1
Host: tile.openstreetmap.org
User-Agent: Dalica/1.1.0        the version of your copy
Accept: */*
Accept-Encoding: identity
Connection: close
  • The User-Agent is the program's name and version, nothing about you, your machine or your system. The four header names User-Agent, Accept, Accept-Encoding and Range are the only ones a request can carry, plus Host and Connection that HTTP itself needs. Range is used only to resume a download pinned to a checksum (face models), so tiles never send it.
  • No cookie, token, referrer or credential is ever sent, and Dalíca keeps no cookies. Each connection carries one request.
  • TLS is rustls with a pure-Rust crypto provider, TLS 1.2 or 1.3, trusting Mozilla's root certificates compiled into the program, so validation never depends on the system's certificate store. There is no setting or API to turn certificate checks off. The host name is sent in the TLS handshake, as for any HTTPS connection.
  • Addresses must be https. A tile server template without {z}, {x} and {y}, or with a plain http:// address, is refused. Redirects are followed only to https addresses and at most 8 times.
  • Timeouts: 15 seconds to connect, 30 seconds of silence once connected.
  • A proxy (Options ▸ Network: the system's HTTPS_PROXY and NO_PROXY, or a host and port you enter) is used only through CONNECT. The TLS session runs end to end inside the tunnel, so the proxy sees the host and port, never the tile address or the reply. Proxies that ask for a password are not supported.

What the servers can learn

Be clear about what an HTTPS request reveals by its nature. The tile server sees your IP address, the time, the Dalíca version, and the addresses of the tiles you look at. A tile address is a zoom level and a square of the map, so it says which part of the world your Places pane was showing. When you look at the markers of your photos, that is roughly where those photos were taken, at the precision of the tiles on screen. If that matters to you, leave tiles off: the offline layer and typed coordinates do everything except draw streets.

What is never sent: the photos, their file or folder names, captions, tags, people or faces, the coordinates of your photos as numbers, anything from your library or settings, and any identifier of you or your computer. Nothing goes out at start-up, during scans, or while the pane is closed.

Automation follows the same gate and one more: map.allow and a search by name reach outside Dalíca, so when an agent drives the app over the control channel or MCP they are refused unless Dalíca was started with --automation-allow-external. Your own clicks and keys are never refused.

Searching for a place by name

Text in "Search for a place:" that is not a pair of coordinates is a place name for the geocoding service: by default OpenStreetMap's Nominatim, at the address template https://nominatim.openstreetmap.org/search?format=jsonv2&q={query}. It is covered by the same Allow map tiles switch and needs the Places pane open; otherwise the search is refused and nothing is asked.

  1. Only on Enter. Nothing is looked up as you type. The text is trimmed and may be at most 512 bytes.
  2. Encoding. The text is UTF-8 and percent-encoded (letters, digits and -._~ kept), then put in place of {query}. This text, and nothing else, is what the service receives about your search.
  3. Memory first. The last 32 searches of the session are answered from memory with no request at all. Otherwise the disk cache is checked: each reply is kept as q-<16 hex digits>.json (the FNV-1a hash of the full address) and reused for 30 days.
  4. One request a second. Nominatim's usage policy asks for at most one request a second, so every search in the process takes turns: a request waits until no other is on its way and a full second has passed since the last one ended (counting from the end means a slow start never shortens the gap at the server). Each search gets one attempt, since a retry would come sooner than the interval. A new search cancels the one on its way.
  5. The reply is hostile until proven otherwise: at most 1 MiB, arrays and objects nested at most 32 deep (checked by a byte scan before the JSON parser sees it), at most 20 results. Each result needs lat and lon on the globe (numbers, or strings of numbers) and a name; its name is cut to 256 bytes and its display_name to 1 KiB at a character boundary. Entries that do not fit are passed over; a reply that is not a JSON list is an error, never a crash.
  6. Picking a result puts the pin there and moves the map to it, zoomed in to at least level 12. From there it is an ordinary geotag: "Put %d photos here?" and one undo step.

Privacy in the logs: the text you searched for and the places found are never written to the log. A failed search logs only its reason.

The same rules apply to a tile server or geocoder you host yourself: both address templates are editable in Options ▸ Network (at most 2,048 bytes each, with an attribution line of up to 256 bytes), and the cache gives each address its own folder.

Names in the library search

Place searches by name go one way only: from a name to coordinates. Dalíca does not turn your photos' coordinates into place names (there is no reverse geocoding), so typing "Reykjavík" in the library's search box does not find photos by their GPS. It does find the free-text Place field of folders and albums (from their Properties), which is indexed with their names and descriptions, and is separate from geotags.
