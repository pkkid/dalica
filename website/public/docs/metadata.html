Metadata in your files

Captions, tags, places, dates and named faces live in two places at once: in Dalíca's own sidecar file and inside the photos themselves, as standard XMP, IPTC and EXIF. This chapter explains which fields are read and written, how a write merges into data other applications left there, why it never touches a pixel, and what happens when the two copies disagree.

Three homes for the same facts

Everything you say about a photo is first recorded in the folder sidecar, a small JSON file named .dalica.json in the photo's own folder. That file is Dalíca's record: stars, captions, tags, places, date corrections, faces, hidden flags, edit recipes and album membership all live there, so a folder carries its data with it when you copy it to another disk.

A subset of those facts is also written into the photo file, in the standard metadata blocks every photo application reads: XMP, IPTC and EXIF. That is how a caption you type in Dalíca shows up in another program, and how tags another program wrote show up in Dalíca. Only the fields in the table below go into files, and each one follows its own option.

The third home is the library index, a cache in the library directory. It holds a copy of everything above for speed, plus things that exist only there: search facts (camera, video, geotagged), content digests, and the last-synced hashes that let Dalíca tell your changes from another application's (see Conflicts). Deleting the index loses nothing but time: a rescan rebuilds it from the sidecars and the files.

The fields Dalíca reads and writes

Each field can come from several places in a file. When a file has more than one, Dalíca takes the first source that has a value, in the order shown. The order is deliberate: for the date and the place, the camera's own EXIF value wins over the XMP copy, because XMP copies of EXIF fields are often stale. For captions, tags and ratings, XMP wins over IPTC and EXIF, because XMP is where current applications keep them.

A few details matter in practice:

  • Camera placeholders are not captions. Many cameras fill EXIF ImageDescription with text such as DIGITAL CAMERA, a generic word like IMAGE or PHOTO, or the camera's own make or model. Dalíca keeps a list of 18 such strings and also ignores a description equal to the make, the model, or the make followed by "DIGITAL CAMERA" (case and surrounding spaces ignored), so your photos do not all arrive captioned with a brand name.
  • A star is a yes or no; a rating is a number. A file rating of 5 imports as a star. Ratings 1 to 4, and the "rejected" value of -1, are shown in Properties and left alone. When Dalíca unstars a photo it writes 0 only if the file says 5 (the value Dalíca would have set), so another application's 3-star rating survives you unstarring a photo there.
  • Tags are flat. Dalíca writes dc:subject only. Hierarchical keyword lists other applications keep in their own properties are left as they are, so such a list can still name a tag you removed in Dalíca.
  • Languages are kept. dc:description can hold one caption per language. Dalíca writes the x-default entry and keeps every other language untouched.
  • Text from a file is cleaned. Control characters (other than tab and line breaks) and the two characters XML forbids are dropped, surrounding spaces trimmed, and tags compared without case, the first spelling kept. Inside the library a caption is at most 16 KiB, a tag at most 256 bytes and a photo has at most 1,000 tags.

How a write happens

Changing a caption does not rewrite the file on the spot. The change goes into the folder sidecar first (your record is safe at that point), and a write request goes into a queue that runs on its own thread, named dalica-metadata-writes, so the window never waits for the disk.

  1. Collect. Each command that changes an owned field (undo and redo included) queues one request per photo with the fields whose option is on. Changes that came from the files themselves, during scans and imports, are never written back.
  2. Wait one second. A photo is written once it has been left alone for 1 second. Typing a caption and then adding three tags therefore costs one write, not four.
  3. Re-read. The file is read again from disk (never a cached copy), up to 1 GiB. A symbolic link is refused: Dalíca does not write through links. If the file changed while being read, the request goes back in the queue.
  4. Decide per field. The file's current values are compared with Dalíca's and with the last-synced hashes (see Conflicts). A field another application changed is imported instead of written.
  5. Merge. Only the metadata blocks are rebuilt, in memory, keeping everything Dalíca does not own. If the file's EXIF, XMP or IPTC block cannot be read, the file is not rewritten at all, because its contents could not be preserved.
  6. Verify. Before the new bytes may replace anything, Dalíca re-reads them: the same container, every metadata block readable, every byte outside the metadata unchanged, and every field it changed reading back as requested.
  7. Replace atomically. The new file is written to a temporary file in the same folder, flushed to disk and renamed over the old one. The file's modification time is put back afterwards, unless you turn on "Update file modification time on metadata changes" (off by default).
  8. Record. The new hashes become the last-synced values, and the library takes the file's new size and time, so the next scan does not mistake Dalíca's own write for an outside change.

Due writes run as a job labeled "Writing metadata", with progress and a Cancel button. Cancel drops the writes not made yet; the folder sidecar keeps those values, and the next change of the field writes it. A photo on a disconnected drive waits: the queue looks again every 10 seconds and the write lands when the drive returns. When the library closes, the writer finishes what is still queued first. A failed write shows a caution toast naming the file and the fields, and the sidecar stays the record.

Why queue at all: a photo file can be tens of megabytes. Rewriting it on every keystroke would be slow, would wear out flash storage and would race with backup and sync tools that watch the folder. One verified write per quiet second keeps the file current without any of that.

Merge, never replace

A file's metadata belongs to you and to every application that has written it. Dalíca owns only these properties, and only while their option is on: dc:description, dc:subject, xmp:Rating (under the star rule), exif:GPSLatitude, exif:GPSLongitude, exif:DateTimeOriginal, photoshop:DateCreated, xmp:CreateDate (only on a date change), the Face entries of the MWG region list, IPTC 1:90, 2:25 and 2:120, and in EXIF the GPS latitude and longitude tags plus DateTimeOriginal and DateTimeDigitized. Every XMP write also sets xmp:MetadataDate to the time of the write. Dalíca writes no private namespace of its own: anything Dalíca-specific stays in .dalica.json.

Inside XMP

Owned properties go into one rdf:Description of Dalíca's own. If another application wrote the same property in its description, it is moved out of there; that description otherwise stays as it was. A write moves only what it sets or clears, so writing tags leaves another application's caption where it is. Clearing a value in Dalíca (an empty caption, the last tag removed) removes the property from the file. Writing the same values again changes nothing, not even xmp:MetadataDate.

The packet wrapper and its padding are reused, so a rewrite can stay in place: the padding grows or shrinks by the change in size and the packet keeps its length while the padding lasts. A new packet gets 2 KiB of padding.

Here is a real run. A test JPEG arrived with an XMP packet "from another application": a caption in two languages, a rating of 3, and two properties in a private namespace. Dalíca imported the caption on the first scan, and then the tags Kyoto and temple were added in Dalíca. This is the packet after the write (namespace declarations left out for width):

<!-- the other application's description: untouched -->

The caption stayed in the other description because only the tags changed. The rating of 3 was not turned into anything. The XMP segment of the JPEG was 1,215 bytes before and 1,215 bytes after: the new description was paid for out of the padding, which went from 514 to 190 bytes, so nothing after the segment had to move inside it. The file grew by 94 bytes only because a new IPTC block was added for the tags.

Inside IPTC

IPTC lives in an image resource block (resource 0x0404) inside the JPEG's APP13 segment. Other image resources are kept byte for byte, and the IPTC digest resource (0x0425) is updated to match (added when the file had none), so other applications do not treat the IPTC as stale. Dalíca's 2:120 takes the place of the first old caption, its 2:25 datasets take the place of the first old keyword, and every other dataset keeps its bytes and its position.

When Dalíca writes IPTC it also writes 1:90 CodedCharacterSet = UTF-8. Older IPTC without that declaration is read as UTF-8 when it is valid and as Latin-1 otherwise; when Dalíca adds the declaration to such a stream, it re-encodes the record-2 text datasets that are not valid UTF-8 from Latin-1 to UTF-8, so every one reads the same text afterwards (binary datasets are never touched). IPTC has length limits that XMP does not: a caption over 2,000 bytes or a keyword over 64 bytes is written in full to XMP and cut at a character boundary in IPTC. IPTC is written whenever a caption or tags change, even into a file that had none, for older tools that read only IPTC.

Inside EXIF

EXIF is edited in place or appended, never repacked. Camera maker notes often contain absolute offsets into the EXIF block, so moving existing data would silently corrupt them. A changed value of the same size is overwritten where it is; a new or larger value (a GPS directory, a date) is appended at the end of the block with only the pointer to it updated. When Dalíca replaces or removes a value, the old bytes are zeroed if nothing else points at them, so a removed location does not linger in the file. A new EXIF directory starts with ExifVersion 0232, a new GPS directory with GPSVersionID 2.3.0.0. Removing a place deletes the latitude and longitude tags and their refs, and leaves altitude, GPS time and direction alone.

An EXIF ImageDescription that reads as a real caption is treated as a copy of the caption: a new caption replaces it and a cleared caption removes it. Otherwise the read order above would bring the old text back as the caption. A camera placeholder is left alone, and Dalíca never adds an ImageDescription that was not there.

Never touching pixels

A metadata write rewrites only the metadata segments: in a JPEG the first EXIF APP1, the first XMP APP1 and the APP13 segment that holds IPTC; in PNG, WebP and TIFF their equivalent chunks or tags. Everything else, including the compressed image data, ICC profiles, comments, unknown segments and any extra images a phone appended after the main one, is copied unchanged. The verification step enforces it by comparing every byte outside the rewritable spans before and after; if a single one differs, the write is thrown away.

Reading the new blocks back shows exactly the owned fields and nothing more. The EXIF block holds ExifVersion 0232, DateTimeOriginal and DateTimeDigitized both set to 2024:07:15 14:17:00, and a GPS directory with version 2.3.0.0, N 65° 36′ 39.6″ and W 19° 30′ 18″. The XMP packet holds the caption, the tags, the place mirror (65,36.66N, 19,30.3W), the date mirror and xmp:MetadataDate, followed by 2 KiB of padding. The IPTC block holds 1:90 (UTF-8), 2:00 RecordVersion, three 2:25 keywords, the 2:120 caption, and the digest resource. The photo was also starred, but no xmp:Rating appears: "Write stars as ratings" is off by default.

A place or a date alone never starts a new XMP packet; they go into XMP only as mirrors of a packet that exists or is being started for a caption, tags or a rating in the same write. In the run above the packet was started for the caption and tags, so it got the place and date too. Writing the same values twice produces the same bytes.

A JPEG's EXIF and standard XMP must each fit in one APP1 segment, 65,533 bytes including its header. If a change would push a block over, Dalíca first drops the packet's padding; if it still does not fit, the write fails with a toast naming the field and the sidecar keeps the value. Dalíca never drops another application's data to make room. In a phone photo with an MPF index (the table that finds the extra images stored after the main one), nothing after the index may change size: new segments always go before it, and a write that would still change the size of something after it is refused, naming the field.

A TIFF is written append-only: nothing outside the first image directory's table and the old values of the XMP and IPTC tags changes or moves, so strips, tiles and maker notes keep their offsets. Because place and date reach a TIFF only through XMP mirrors, a TIFF whose place lives in EXIF is refused for that field before anything is written, with an error naming the field.

Turning it off

Each kind of write has its own option in Options, General, Files (and Options, People for names). With an option off, Dalíca still reads that field from files and imports it as usual, but never writes it. Your values stay in the folder sidecar either way.

Turning an option on writes nothing by itself: the next change of a field writes it. Read-only files and offline volumes are never written whatever the options say; their values stay in the sidecar, and writes for an offline volume wait until it returns.

Why the file time stays: many people sort or back up by modification time. A caption should not make a ten-year-old photo look like it was taken today, so by default the old time is put back after the rename.

When the sidecar and the file disagree

Two copies of the same fact can drift apart: you edit a caption in another program, or a sync tool brings back an older file. Dalíca resolves each field on its own with three values: the file's value, Dalíca's value, and the last-synced hash, a 64-bit FNV-1a hash of the value as it was last read from or written to the file, kept per photo and per field in the index. (Tags hash as a set, since order in an XMP bag means nothing; a place hashes to the micro-degree; a date as its ISO text.)

SituationResult
File and Dalíca agreenothing to do
First scan: the photo has no entry in its folder sidecar yetevery value in the file is imported (this is how captions, tags, places, dates, ratings of 5 and named faces from other programs arrive)

No last-synced hash (the index was rebuilt)the sidecar wins and is written on the next write of that field

Two exceptions protect data. A date is never removed from a file: if Dalíca has no date, the file's date stays. And a place you removed (stored as "geo": null) is never brought back by a file that still has GPS. A place another application changed follows the file with no undo step, since bringing it in changes nothing you set.

A field whose write option is off may legitimately differ from the file forever; the rules then only decide what Dalíca shows. Rescans only look at a file again when its size or modification time changed, which is why Dalíca records the size and time its own write left: otherwise every write would look like an outside edit.

Which date is "date taken"

A photo's date decides where it sorts, which year it falls under and what the timeline shows, so Dalíca is careful about where it comes from. The date you see is the first of these that exists:

The scan reads the EXIF DateTimeOriginal straight from the photo's header and keeps it as the file's date. Where the full metadata read finds a different answer (for example a photo whose only date is in XMP), that answer becomes the photo's date, recorded as a date of Dalíca's because it differs from the header's. Offsets from UTC (OffsetTimeOriginal, or the zone in an ISO 8601 XMP date) are accepted up to ±18 hours, fractions of a second up to nine digits. A malformed date, such as the 0000:00:00 00:00:00 some cameras write when their clock was never set, counts as no date.

What the date commands change

Adjust Date and Time runs one command, photo.dates.set, in one of two forms: shift every selected photo by the same number of seconds from its own effective date, or set them all to one date and time. The new value is stored as your date in the folder sidecar ("date"); the file's own date is kept beside it. A new date equal to the file's own date clears your date instead, so shifting forward and back again leaves nothing behind. All photos change in one undo step and re-sort at once.

With "Write date changes to files" on, the write-back then puts the date into the file: EXIF DateTimeOriginal and DateTimeDigitized both get it, the file's existing offset from UTC is kept (it is the camera's time zone), and the sub-second fraction is dropped because Dalíca's dates are to the second. The XMP mirrors exif:DateTimeOriginal, photoshop:DateCreated and xmp:CreateDate are updated when the file already has them. Once that write lands and the file is scanned again, the file's own date equals yours. Undo then sets the old date back and the write-back puts the old date back in the file, so undo works whether or not the write had happened yet.

XMP sidecars for RAW files

Dalíca never modifies a RAW file. With "Write XMP sidecars for RAW files" on, the owned fields of a RAW go into an XMP file next to it instead.

  • Name. <stem>.xmp (IMG_0001.CR3 gets IMG_0001.xmp), the name most applications use. Reading also accepts IMG_0001.CR3.xmp and an upper-case .XMP, and an existing sidecar is written back under its own name. In a RAW+JPEG pair the stem sidecar belongs to the RAW; the JPEG keeps its metadata inside itself. When several RAWs share a stem, the one named exactly the stem gets <stem>.xmp (else the first by name) and the others use <file>.xmp, so two photos never share a sidecar. Names are compared without case.
  • Merge. An existing sidecar is merged into exactly like a packet inside a photo: raw converters' develop settings, history and every other namespace stay byte for byte. A new sidecar starts as a copy of the XMP embedded in the RAW (a DNG has one), so the sidecar once created is the RAW's whole XMP; otherwise it starts as a plain x:xmpmeta document without wrapper or padding. A write that changes nothing creates no sidecar.
  • Reading happens on every scan whatever the option says. The sidecar replaces the embedded packet as a whole rather than field by field, so a value cleared in the sidecar stays cleared. The RAW's own EXIF still comes first for date and place.
  • Damage. A sidecar that is not well-formed XMP is kept aside as <name>.xmp.corrupt-<time> and a new one is written on the next write; meanwhile the embedded XMP is read. A blank one counts as none. One that cannot be read at all (permissions) is left alone and the write fails.
  • Moving. Moving, copying or renaming a RAW inside Dalíca takes its sidecar along, renamed to match, and undo brings it back. A sidecar name already taken at the destination is never overwritten. Deleting a RAW leaves its .xmp where it is: the trash takes only what you chose.

Named faces in files (MWG regions)

Most photo applications store named faces in the Metadata Working Group region schema, mwg-rs:Regions. Dalíca reads it always and writes it only with "Store people names in photos" on (or once, for a selection, with Tools, Experimental, Write People Names to Photos..., which asks first).

Reading

Entries of type Face become face rectangles, and a mwg-rs:Name becomes a person (matched to an existing person by name ignoring case, else created; an unnamed entry goes to Unnamed). The area stArea:x, y is the box center and w, h its size, normalized to the photo. Areas in pixels are divided by mwg-rs:AppliedToDimensions and skipped without it, as are points, circles and boxes with no positive size. Boxes are clipped to the photo. Entries of other types (pets, focus areas, barcodes) are kept in the file and ignored. Only the first top-level region list counts, and at most 256 faces are read.

Regions describe the upright photo, the same frame Dalíca's sidecar uses, so they need no conversion, with one exception. Some applications give the box in the sensor's frame and say so with mwg-rs:Rotation. Dalíca turns such a box back to upright:

mwg-rs:RotationEXIF orientation it goes withUpright box from (x, y, w, h)
-π/26(1 - y, x, h, w)
+π/28(y, 1 - x, h, w)
±π3(1 - x, 1 - y, w, h)

The angle is taken modulo 2π to within 0.05 radians; any other angle, and mirrored orientations, are taken as written.

On a photo's first scan the file's faces become its faces when the folder sidecar gives it none. Later, when a known photo's file changes, faces in the file that overlap none of the photo's faces come in. Both arrive with no undo step and are never written back.

Writing

Only named faces are written; unnamed and ignored faces never are. Each named face takes the existing Face entry that overlaps it with an intersection-over-union of at least 0.5 (one already carrying its name first, then the closest). A matched entry keeps every other field byte for byte and gets Dalíca's name and box only where they differ (boxes compared to within 10-5), written in the entry's own unit and rotation. Unmatched named faces are appended with a normalized area. Readable face entries with no counterpart are removed, because Dalíca imports anything new before every write, so such an entry is a face you removed or ignored. Face entries Dalíca cannot read were never imported, so they stay. mwg-rs:AppliedToDimensions is kept when present and added (the upright pixel size) when missing. At most 256 faces are written, and writing the same faces again changes nothing.

The library keeps no last-synced hash for faces, so a new face from another application is detected by overlap instead: a write knows every rectangle the photo had before and after your change, and a file holding a face entry none of them overlaps is not written over. That face is imported first, and the write is made again.

Privacy: names are personal data that travel with a file when you share it. That is why writing them is off by default. Face recognition data itself (embeddings) never goes into a photo file.

Sidecars left by the classic organizer

Folders managed by the classic folder-based organizer often contain a hidden per-folder INI file of its own, and sometimes a hidden originals directory. They can hold years of stars, captions, rotations, crops, edit lists, face rectangles, person names, album memberships and album definitions. Dalíca reads them so that this work is not lost, and never writes them: not modified, renamed, set aside or deleted, so you can still run the old program on the same folders.

When it is read

During every scan, automatically; there is no import step. The setting "Read photo data left by the previous organizer" (Options, General, Files, on by default) turns it off, and toggling it rescans so the data leaves or returns without anything being written.

A scan alone never writes into a legacy-only folder. The first .dalica.json appears with your first change there, and it carries everything the legacy file held for the folder, not just the photo you changed. Dalíca prints it, parses it back and checks it says the same before committing it with an operation that cannot replace an existing file; if a .dalica.json appeared in the meantime (made by another program or a sync tool), that file wins and the folder is read again from it. From then on the folder reads .dalica.json, and later changes the old program makes to its own file are not picked up.

What is read, and how

  • Per photo: star, hidden flag, caption, tags, rotation, mirror flag, crop, the edit list and its redo list, faces with their person, album memberships and the geotag. Sections are matched to files by exact name, else ignoring case when that matches exactly one.
  • Per folder: description, date, place and whether it was hidden; album definitions; and the names of the contacts its faces point to (from the folder's own file, then its ancestors').
  • Edits are mapped to Dalíca operations where an equivalent exists, with parameters converted linearly from the old control's range. Anything without a confident equivalent is kept verbatim as a legacy:<name>(...) entry in its place in the recipe, so the order is preserved and nothing after it is lost; the edit panel shows how many such entries a photo has. Rotation and mirror become the first operations of the recipe, and only the last crop of the list is carried.
  • Faces in the legacy file are stored in the photo's raw pixel frame, so they are turned through the photo's EXIF orientation into Dalíca's upright frame.
  • Albums and people become Dalíca albums and people, matched by their legacy id, so the same album seen in many folders is one album. A person is found by that id, else by name ignoring case, else created.
  • The legacy originals directory is recognized and offered as the original for Revert and Undo Save. Dalíca copies the original back from it and never writes into it or removes anything from it.

The reader is bounded like every reader of outside input: the file at most 64 MiB, a line at most 1 MiB, at most 1,000,000 sections and 1,000 keys in a section. A file over a limit is reported and skipped whole. Text is read as UTF-8 when the file says so and as Windows-1252 otherwise; a value with bytes that do not decode is left out, so mangled text never reaches a file Dalíca writes.
