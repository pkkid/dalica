# dalica-thumbs

**Layer L2.** The prioritised, de-duplicating job pool, the in-memory LRU and the on-disk thumbnail cache.

- **May depend on:** `image`, `edit`, `fs`, `core` (`docs/architecture.md` §2; `cargo xtask layers` enforces it).
- **Public API (M1.12):**
  - `Pool<K, T>`: `new(workers)` (`default_workers()` = cores − 1, clamped 2..=8), `submit(key, Priority, work)` → `Queued` / `Merged` (priority raised) / `Running`, `cancel(key)`, `queued()`, `try_recv()` / `recv_timeout()` for `(key, result)`. Highest priority first, first come first served within one; one job per key; a cancelled job is never delivered; dropping the pool cancels running jobs and joins the workers. `Priority` constants follow `architecture.md` §5.
  - `Lru<K, V>`: byte budget never exceeded, least recently used evicted first, an entry larger than the budget refused.
  - `thumbnail(path, long_side, &Limits)` → upright `Rgba8` (the thumbnail job).
- **Public API (M4.3), `pack`:** the packed disk cache of `architecture.md` §6.6.
  - `Cache::open(dir, Options)` takes `<dir>/lock` (a second process gets `Fs(Locked)`) and loads one pack + index per `Size` (`S128`, `S256`, `S512`, `S1024`, `Screen`); `get` / `contains` / `put` / `remove` / `remove_all(key)` / `sync`; `stats(size)`, `disk_bytes()`; `compaction_due`, `compact(size)`, `prune()` and `maintain()` (the background job: compact what passed 25 % dead, then prune past the 2 GiB budget down to 80 %, largest sizes first, oldest entries first). `Sync`: one lock per size, held for one lookup and one read or append.
  - `Key::new(path, file_size, mtime_ns, recipe_hash, renderer_version)`: the content-addressed key (§6.4), a stable 128-bit FNV-1a. Entries are opaque bytes; the ladder stores JPEG at `QUALITY` (90).
  - Files: `<size>-<generation as 8 hex>.pack` (16-byte header, entry bytes) and `.idx` (16-byte header, 40-byte records each with its own CRC-32; a torn tail is cut, a damaged record costs only its entry). An entry's bytes carry a CRC-32 checked on the first read in a process (a mismatch is a miss). A compaction writes generation n + 1 beside n through `fs` temporary files (pack first, then index; a generation counts only once its index exists) while gets and puts go on. Only names of this shape (`is_own_name`) are ever listed or deleted.
  - Bench: `cargo bench -p dalica-thumbs --bench pack [-- --count N --bytes N --json]` reads 100 k entries packed and as loose files.
- **Public API (M4.1), `sketch`:** the colour sketch of `architecture.md` §6.5: `encode(&Rgba8)` → at most `MAX_BYTES` (32; 24–26 in practice) bytes in the ThumbHash style (version byte, aspect code, DC and AC terms), `decode(bytes)` → `Sketch` (the colours of a small grid, at most `MAX_DECODE_SIDE` a side) for drawing as a mesh the same frame. Hostile bytes give `Err`, never a panic.
- **Public API (M4.8), `ladder`:** the size ladder of §6.5. `covering(need, screen)` (the smallest size at least `need` long) and `choose(need, screen, has)` (`Covers`, `Smaller` to scale up, `Nothing`); `prefetch(visible, len, velocity)` (one screen plus `LOOKAHEAD_SECS` of travel ahead, at most `MAX_AHEAD_SCREENS`, half a screen behind); the two jobs, `scan` (one decode makes the 128 and 256 entries and the sketch; cached entries are not made again) and `fetch` (one size from the cache, else decoded and stored); `Source { path, file_size, mtime_ms }.key()`, `entry_key(key, size, screen)` (the screen-size entry's key holds the display's size), `encode_jpeg` / `decode_entry`. `RENDERER_VERSION` is part of every key.
- **M5.16, rendering options:** `Render { color_managed }` (View → Use Color Management; default on) goes into the key through `Source::key_for(&render)` (the default render gives the same key as `key()`, so existing entries stay valid) and into the decode through `scan_with` / `fetch_with` and `thumbnail_with(path, long_side, &DecodeOptions, &Limits)`.
- **M7.9, edited photos:** `Edits { recipe, key }` is a photo's recipe without its rotations and flips (the cells turn the picture as they paint it, so a rotation never remakes a thumbnail) and that recipe's `edit` render key; `Edits::of(&edits)` (`None` when nothing but rotations and flips is left, or the recipe cannot be read), `Edits::with_versions` (what a version bump would change), `Edits::from_recipe`. `Source::key_edited(&render, Option<&Edits>)` folds the recipe hash and the operations' versions into the key (unedited photos keep `key_for`'s), so a new version of one operation remakes only the photos that use it. `scan_edited` / `fetch_edited` make the entries and the sketch of an edited photo with `render_edited(source, render, edits, long_side, limits)`: `edit::render` (the edit view's renderer) of the photo decoded to fit, or decoded larger in proportion, at most `MAX_EDIT_SOURCE` (4096), when the edits keep only part of it. `scan_with` / `fetch_with` are these with no edits. A 24 MP JPEG's scan takes the same time edited as not (≈ 87 ms in release, Auto Fix as the recipe, 2026-10-13).
- **M5.16, `upkeep`:** the cache's pruning policy and forgetting, run on pool workers. `Budget { bytes, prune_to_percent }` (`Budget::of` clamps the cache size setting to `MIN_BUDGET` 64 MiB ..= `MAX_BUDGET` 1 TiB; 2 GiB and 80 % by default); `over(cache, &budget)`; `prune(cache, &budget, keep)` takes a cache past its budget down to 80 % of it, the largest sizes first and the oldest entries of a size first, stepping over the entries `keep(size, key)` names (the photos of folders that cannot be reached), then compacts what it took from, and reports `Pruned { sizes, removed, kept, before, after }`; `forget(cache, &[(size, key)])` makes the entries of photos that left dead. Both only ever remove cache entries (through `Cache`, which lists and deletes only its own file names); a cache shared by several libraries loses another library's entries only to pruning, by age. `Cache::entries(size)` lists a size's live entries oldest first (from memory) for the policy.
- **Packed reads against loose files (M5.16, the M4.R question):** the pack is not slower. With the page cache warm for both stores it reads faster in order and shuffled (100 k entries of 6 KB, µs per read: pack 0.74 and 1.06, loose 2.15 and 2.48), and with both cold faster still (pack 1.27 and 24.4, loose 67.1 and 71.6). The M4.R runs' slow shuffled pack reads (4.7 and 17.9 µs against 2.5 and 2.7) are reproduced exactly by dropping only the pack's pages while the loose files' stay cached (23.8 against 2.4): the bench writes the loose files last, so under memory pressure the pack's pages go first and a shuffled read waits on the disk, which readahead hides for reads in order. A page-cache artefact of the bench, not of the pack (measured with `posix_fadvise(DONTNEED)` per file on an NVMe disk, 2026-10-12).
- **M15.20, `video`:** poster frames. `plays(code)` / `why_not(code)` (whether this build decodes a clip of that container codec code, by `dalica_image`'s playability: H.264, HEVC with its `hevc` feature); `poster(path, long_side, &Limits)` (`FrameSource::poster`: the first frame of mean luma ≥ 0.06 within 10 s, else the first; upright 8-bit sRGB, never enlarged; read sample by sample, no decoder threads); `scan` and `fetch`, the ladder's two jobs for a clip (`ladder::scan_by` / `fetch_by`: the same entries, sketch and cache, under `Source::key_for`). A clip the decoder refuses is `ladder::Error::Unplayable(reason)`. A 640 × 368 clip's scan (128 + 256 + sketch) takes 3–5 ms in release (2026-10-19).
- **Test it alone:** `cargo test -p dalica-thumbs` (no window, GPU, network or personal photos needed): fake jobs held behind gates show strict priority order, one run per duplicate key, cancellation and a 10 000-job stress run with nothing lost; the LRU against a model; the pack cache in temp folders (round trips at every size, torn and damaged files, compaction alongside puts and gets, pruning next to foreign files, an `fs` fault of each kind the cache copes with differently, hostile bytes); the sketch's round trips and hostile bytes; the ladder's choices, prefetch order and jobs on `scenes` photos; edited photos' keys, and their entries against `edit::render` (`tests/recipe.rs`); upkeep's pruning (stops at 80 %, largest sizes and oldest entries first, kept entries spared, foreign files untouched byte for byte, another library's entries forgotten never and pruned by age); posters of H.264 clips made in the test (`tests/video.rs`). The integration tests are one binary (`tests/all.rs`, one module per file: `cargo test -p dalica-thumbs --test all <file>::` runs one); a task's gate runs them quick, `DALICA_FULL_TESTS=1` at full strength (every property case, every size).
